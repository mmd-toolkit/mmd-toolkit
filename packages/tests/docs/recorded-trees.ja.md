# 変更の記録した木の確かめ

English version: [recorded-trees.md](./recorded-trees.md)

この文書は、
変更が足すか書き換える記録した木（`ast.json`）を確かめるコマンドを説明します。
コマンドは、その木に [`checkTree()`](./check-tree.ja.md) を当てます。
あわせて、木の文書が述べる条件のうち、
`checkTree()` が確かめると示されていないものを、
人が木と照らして読む項目として並べ、変更が書いた答えと照らします。

```sh
pnpm --filter @mmd-toolkit/tests run recorded-trees:check --base <ref> [--places]
```

## なぜ

`checkTree()` が条件を報告するのは、その条件の決まりを持つときだけです。
決まりのない条件を破った木は、問題なしで通ります。
「問題なし」は決まりが守られていることを言い、木が正しいことは言いません。
そこで、木の文書が述べる条件の 1 つ 1 つを、次のどちらかにします。
`checkTree()` が確かめると示す（条件を破った木を `checkTree()`
が報告するテストのケースを名指す）か、変更が記録した木と人が照らして読むかです。
示したものは下の確かめの表に書き、読んだ結果は答えとしてファイルに残します。
答えの漏れは、記憶ではなくコマンドが見つけます。

## 走らせ方

- `--base <ref>` は必ず渡します。
  基点は `<ref>` と `HEAD` の merge base で、変更は、
  作業ツリーのうち基点と違うものすべてです。
  基点の後の commit、commit していないもの、
  git がまだ追跡していないファイルを含みます。
  既定がないので、commit の後に走らせて、何も確かめずに通ることはありません。
  - 記録した直後に、その段の記録だけ: `--base HEAD`。
  - プルリクエストの全体: `--base origin/main`。
- `--places` を付けると、各項目の場所（節点かトークンと、
  そこの入力の文字）をすべて出します。

終了コードは、次のどれかのとき 1 です。
確かめた木に `checkTree()` の問題があるとき、
記録が読めないとき（`ast.json` が JSON でない、`input.mmd` がない）、
値の節点にも構造の節点にも分けられていない節点の型が木にあるとき、
答えのファイルか確かめの表のファイルが読めないとき、
項目か変更の木に答えがないとき。
コマンドの使い方の誤り（`--base` がない、`--base` を 2 度渡した）と、
git のリポジトリの外で走らせたとき、git の誤り（基点がない、
履歴が浅くて merge base が取れない）では 2 です。
それ以外は 0 です。
表の古い行、表がまだ判断していない項目、鍵が変わった項目では落ちません。

## 変更の木

変更の木は、
変更が `input.mmd` か `ast.json` を足すか変えるか消した fixture のうち、
いま `ast.json` があるものです。
道は 1 つずつ比べます（`git diff --no-renames`）。
git の改名の推定は使いません。
記録がたまたま同じ、無関係な 2 つの fixture を組にすることがあるためです。
改名した木も変更の木で、その答えは中身で見つけます（「答え」を参照）。

コマンドは、変更が消した `ast.json` を数え、
変えた `parse-error.json` を読まずに並べます。

## すべての記録した木を確かめるとき

`tools/src/recorded-trees-run.ts`（ランナー）が、木 1 つに確かめを当てます。
ランナーが実行時の import でたどり着くファイル（TypeScript の構文解析で読む。
`tools/src/runtime-imports.ts`）が、確かめの結果を決めます。
変更がランナーかそのファイルのどれかを変えると、
コマンドはすべての記録した木を確かめ、どのファイルによるかを言います。

ランナーがたどり着くファイルは、import と export の宣言で、
相対の道だけを読み込みます。
そのどれかが、パッケージか Node.js の組み込みのモジュールを読み込む、
`import()` を呼ぶ、`import.meta` を使う、大域の名前 `process`、`globalThis`、
`global`、`require`、`eval`、`Function` のどれかを使うときは、
結果を決めるファイルが分かりません。
これらの大域の名前を通して、モジュールは組み込みのモジュール、環境、
走らせるときに作ったコードを読めるためです。
そのときコマンドは、すべての記録した木を確かめ、
そのファイルと読み込みを名指します。
名前は構文木で読むので、
`this.require` のようなメンバーは読み込みではありません。
ランナー自身は、
木のファイルを読むので Node.js の組み込みのモジュールを読み込んでよく、
その種類のほかのものは読み込みません。
読み込んだパッケージの版は、
リポジトリのファイルを変えずに結果を変えうるためです。

## ブロックと項目

木の文書は、`packages/spec/docs/ast.md` と `ast/<図種>.md`、
`packages/parser/docs/tokens.md` と `tokens/<図種>.md`、
`packages/parser/docs/positions.md` と `positions/<図種>.md` の英語版です。
`pnpm run lint:md` と同じく、Markdown として読みます。
ブロックは、リストと表の外の段落、リストの 1 項目（その項目自身の文。
中のリストと表は含まず、その項目と行はそれぞれのブロック）、
表の本文の 1 行です。
`Japanese version: …` の行はブロックではありません。

fixture の引用を除くと空白しか残らない段落は、ブロックではありません。
その引用は、同じ文書で、その段落より前の最後のブロックの場合に足します。
そのブロックが表の行なら、その表の本文のすべての行に引用を足します。
コードと HTML はブロックではないので飛ばします。
前にブロックがなければ、引用はどこにも足しません。

項目は、ブロックと図種の組です。
`<文書>/<図種>.md` のブロックは、その図種に当たります。
`ast.md`、`tokens.md`、`positions.md` のブロックは、
すべての図種と `error`（本体が `ErrorDiagram` の木）に当たります。
木の図種は、その名前の頭の文字を大文字にして `Diagram` を続けたものが、
木の本体の型と同じになる図種です。

項目の場所は、木の中で項目が当たる所です。

- 節点の型を名前とする見出しの下のブロック: その型の節点。
- 最初の見出しの欄が `Kind` の表の行で、
  最初の欄が `tokens.md` のトークンの種類であるもの: その種類のトークンと、
  それを持ついちばん内側の節点。
- ほかのブロック: 木の全体。

場所は、節点なら `<fixture> <型>@<始め>-<終わり>`、
トークンなら `<fixture> <種類>@<始め>-<終わり> in <節点の型>`、
木の全体なら `<fixture> *` と書きます。
木の中に場所がない項目も読みます。
誤った種類のトークンは、その種類の行の場所になり、
持つべき種類の行の場所にはならないためです。

項目の場合は、そのブロックが引く fixture（`[fixture: <diagram>/<name>]`）です。
読むときの手がかりで、答えの一部ではありません。

`packages/spec/docs/common.md` か `packages/spec/docs/diagrams/`
の文書の見出しにリンクするブロックは、その言葉をその節の定めで読みます。
そこで、その節を項目に添えます。
節は、その見出しから、同じ深さかより浅い次の見出しの前までです。
節の anchor は、`pnpm run lint:md` がリンクを確かめるときと同じく、
見出しから作ります。
ルール `markdown-links/no-missing-fragments` が使う `github-slugger`
で作るので、lint が通すリンクは、ここでも節を指します。
anchor のないリンクは、節を指しません。

## 鍵

ブロックの鍵は `<文書>:<ハッシュ>` で、
ハッシュは鍵の本文の SHA-256 の頭の 16 進 12 桁です。
鍵の本文は、次を 1 行ずつ並べたものです。

- ブロックが節点の型の見出しの下にあれば、`under <型>`。
  同じ欄の行でも、2 つの節点の型の下では 2 つの条件を述べるためです。
- ブロックの文。
- ブロックがリンクする節の文を、リンクの順に。
  anchor が見出しを指さないときは `<行き先> names no section`。

どの部分も、fixture の引用を除き、空白の並びを 1 つの空白にします。
表の行では、各セルのソースの文から fixture の引用を除き、
空白の並びを 1 つの空白にし、空になったセルを除いて、
残りを `|` の両側に空白を 1 つずつ置いてつないだものを鍵の文にします。
そのため、引用だけの列を足しても、引用をその列に移しても、鍵は変わりません。
人に示す行の文は、ソースに書かれたままです。
引用は場合を名指すだけで条件を変えず、Prettier は文を折り返し直しうるので、
どちらも鍵を変えません。
1 つの文書の 2 つのブロックの鍵の本文が同じときは、2 つ目のハッシュの後に `.2`、
3 つ目に `.3` を付けます。

項目の鍵は `<ブロックの鍵>@<図種>` です。
木の中身の鍵は `<入力>:<木>` で、
その `input.mmd` と `ast.json` の git の blob の id です。

## 確かめの表

表は、コマンドが作業ツリーと基点の 2 つの版から読むデータです。
答えと同じく読むので、答えと並べて置きます。
`packages/tests/recorded-trees/coverage-table/` に、
木の文書ごとに 1 つの JSON のファイルを置き、
文書の名前で呼びます（`packages/parser/docs/positions.md` なら
`parser-positions.json`）。
どのファイルも、リスト `rows` を持つオブジェクトです。
行は、1 つのブロック（`block`、その鍵）の、
名指した図種（`diagrams`）についての判断を 1 つ持ちます。
図種はどれも名指すので、後で足された図種は、行がそれを名指すまで判断されません。
`about` は、表を読む人のためのブロックの書き出しで、比べません。
判断は次のどれかです。

- `shown`: ブロックが分けるすべての場合を、
  `cases` に
  `{ "case": "<条件を言葉で>", "tests": [{ "file": "…", "text": "…" }] }`
  として名指します。
  `case` はブロックの言葉による空でない文字列で、
  `tests` は 1 つ以上のテストへの参照です。
  各テストは、その場合の、
  このブロックの条件を破った木を `checkTree()` が報告することを示します。
  別のブロックの条件を破っても、この場合を示したことにはなりません。
  許し（`may`）と語の定義そのものは、場合ではありません。
  木をたどる道具がすること（訪ねる順や飛ばすもの）、仕様の文書の書き方、
  パーサーが入力を受理するかを述べる文も、木の場合ではありません。
  `checkTree()` が受け取るのは入力の文字列と木だけで、
  これらを破る木はないからです。
  テストは、`packages/tests/tests/` のファイル（`file`）と、
  そのファイルにある文字列（`text`）で名指します。
  文字列は、ファイルに書かれたテストの題や、壊す fixture の名前などです。
  文字列はファイルの文の中で探すので、走らせるときに組み立てる題では、
  テストを名指せません。
- `not-shown`: 理由（`reason`）と、その説明（`note`）。
  `no-rule` は、条件についての `checkTree()` の決まりがないこと。
  `rule-misses-condition` は、決まりはあるが、
  条件の一部を破ったケースが報告されないこと。
- `no-condition`: 名指した図種について、ブロックが木の条件を述べないこと。
  節点、欄、値、トークン、位置のどれについても何も言わないか、
  その図種には場合がありません。
  `kind` がその理由を言い、`note` を添えます。
  `introduction` は、文書かその一部を紹介すること。
  `pointer` は、条件を持つ文書か節を指すこと。
  `reason` は、ほかの文の理由を言うこと。
  `not-in-diagram` は、ブロックの述べる節点の型、欄、トークンの種類を、
  その図種の文書が定めず、その木に場合がないこと。
  `note` には、どの文書が何を定めないかを書きます。
  その図種の文書が後でそれを定めても、新しいブロックはそれぞれ判断されるので、
  この行は残ってかまいません。
  条件の例として書かれた文は、その条件の場合の 1 つです。
  条件と紹介が混じるブロックは、条件を述べます。

[欄の書き方](../../spec/docs/ast.ja.md#欄の書き方) の型の書き方は、
表の欄の条件を定めます。
そのブロックは条件として判断するので、型の意味が変われば、
その項目はまた読まれます。
場合は、その書き方が述べる値の種類と、リストや `null` の位置を分けます。

コマンドは、表のファイルを読むときに、どれも確かめます。
JSON でないファイルや、行がこの形でないか、文書にない図種を名指すファイルは、
行を与えず、読めない答えのファイルと同じく、確かめを落とします。

行のない項目は、まだ判断していない項目です。
行が数えられるのは、そのブロックがいまその鍵を持ち、
名指した各場合のテストがどれもまだそのファイルにあり、
ブロックが行の図種のそれぞれに当たり、
前の行がその項目を覆っていないときだけです。
そうでない行は古い行で、コマンドはそれを並べ、その項目はまた読まれます。
読む項目は、`shown` でも `no-condition` でもない項目です（判断していても、
していなくても）。

行を古くする変更や、ブロックを足す変更では、
同じプルリクエストで `packages/tests` が判断し直します。
確かめの表は、木の文書の共有の形です。
その変更のレビューは、基点にすでにあるものとは別に、
その変更が増やした古い行とまだ判断していない項目を、
コマンドが並べないことを確かめます。
コマンドはそれで落ちません。
文書だけの変更を、機械が止めないためです。

## 答え

変更の答えは、
`packages/tests/recorded-trees/answers/` の 1
つのファイル（`<名前>.json`）にあります。
変更がマージされた後も残し、後の変更で書き換えません。

```json
{
  "items": [
    {
      "item": "packages/spec/docs/ast/er.md:0123456789ab@er",
      "trees": [
        { "key": "<input blob>:<tree blob>", "fixture": "er/gram-alias" }
      ],
      "answer": "…"
    }
  ],
  "trees": [
    {
      "key": "<input blob>:<tree blob>",
      "fixture": "er/gram-alias",
      "answer": "…"
    }
  ]
}
```

- `items` は項目への答えです。
  項目ごとに 1 つで、中身の鍵で名指した木を覆います。
- `trees` は、変更の木ごとに、その fixture を引く文と照らして読んだ答えです。
- `fixture` は、ファイルを読む人のためのものです。
  比べません。
  改名した木もその中身で覆われ、名前が古くなっても直しません。
- 文が空か空白だけの答えは、コマンドが出す雛形のとおりのもので、
  何にも答えません。

項目に変更の木への答えがあるのは、どれかのファイルの答えが、
その項目と木の中身の鍵を覆うときです。
変更の木に答えがあるのは、`trees` のどれかがその中身の鍵を覆うときです。
答えの文に何を書くかは、記録の作業の手順が定め、ここでは定めません。

- 基点にあるファイルの答えは、その項目に答え終えています。
  項目はもう求められず、コマンドは鍵だけを並べます。
  改名したか移した木は、こうして覆われます。
- 変更が足した答えがあっても、項目は並べたままで、変更が答えたことを添えます。
  レビューする人が、答えを先に読まずに、同じ項目を読むためです。
- 項目の鍵か中身の鍵がもう合わない答えは、使わず、落とさず、消しません。
  その時に何が読まれたかの記録になります。

レビューする人の答えは、このファイルではなく、レビューの報告に書きます。

## 出すもの

コマンドは Markdown を出します。
端末でも CI のログでも同じです。

1. 確かめた木: 変更の木か、すべての記録した木とその理由。
2. 数: 確かめた木、図種ごとの変更の木、消えた `ast.json`、
   変わった `parse-error.json`。
3. 問題: `checkTree()` の問題とその木、読めない記録、分けられていない節点の型、
   読めない答えのファイルと確かめの表のファイル。
4. 読む項目（図種ごと）: 鍵、文書と行、判断（示せない、かまだ判断していない）、
   ブロックの書き出し、場所の数、場合、あわせて読む節、変更の答えが覆うか。
   `--places` では場所そのもの。
   続けて、基点が答えた項目。
5. 変更の木ごとに、その fixture を引く文。
   `packages/spec/docs`、`packages/parser/docs`、
   `packages/tests/docs` の文書の `[fixture: <diagram>/<name>]` と、
   `packages/prettier-plugin-mmd/docs` の文書の
   `[corpus fixture: <diagram>/<name>]` です。
   整形ツールの文書の `[fixture: <diagram>/<name>]` は、
   整形ツール自身の fixture を名指します。
   どの文も引かない木では、その fixture を変更が足したかと、
   集めた入力かを言います。
   集めた入力かは `expected.json` の `source.kind` で読みます。
   集めた入力（`mermaid`）は、文に引かなくてよい fixture です。
   書いた入力（`authored`）は、集めた入力ではありません。
   source の種類が読めなければ、分からないと言います。
   変更が足した、どの文も引かない書いた入力だけに、
   引く文が要ると `packages/spec` へ伝えるよう促します。
6. ない答えと、鍵を埋めて答えを空にした答えのファイルの雛形。
   コマンドはファイルを書きません。
7. 確かめの表の古い行と、その理由。
   先に、変更が古くしたか足した行、次に、基点でも古い行です。
   行は、基点の表を、基点の文書とテストのファイルで読んだものと比べます。
   変更がそのどれも変えないときは、古い行はどれも基点のものです。
8. 表がまだ判断していない、すべての文書の項目（文書と行ごと）。
   先に、変更が足したか、基点では判断していたのに判断していない項目、次に、
   基点でも判断していない項目です。
9. 基点から鍵が変わった項目と、何が変わったか（ブロックの文か、どの節か）、
   新しい文と照らして読む fixture。
   ブロック自身の文が変わったときは、そのブロックが引く fixture です。
   変わった節では、2 つの版の一方にだけあるブロックが、
   その版で引く fixture のうち、項目の図種のものです。
   節だけが変わったときは、
   ブロック自身が引く fixture は変わった文の場合を表さないので、読みません。
   fixture ごとに中身の鍵を出し、木がないか、もうないときはそう言います。
   `--places` では、その木の中の項目の場所も出します。
10. 変更の `parse-error.json`。
    コマンドはこれを読みません。

## 表を判断し終えるまで

確かめの表のすべての項目を判断し終えるまでは、
`tests/check-tree-corpus.test.ts` が、テストを走らせるたびに、
すべての記録した木に `checkTree()` を当てます。
このコマンドは、まだ CI に入りません。
