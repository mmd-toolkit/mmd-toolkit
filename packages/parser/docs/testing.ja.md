# パーサーのテスト

英語版: [testing.md](./testing.md)

テストは `tests/` にあります。
パーサーを、[`@mmd-toolkit/tests`](../../tests) の fixture と、
pin した mermaid.js（12.0.0）に照らして確かめます。

## fixture

テストは、`common/`、`flowchart/`、`sequence/`、`class/` のすべての fixture を
parse し、次を確かめます。

- 受理・拒否
- 図種
- Db の要約
- 木の不変条件（[木の不変条件](#木の不変条件)を参照）

Db の要約は、木から組み立てます。

- テストは、図の Db normalization の手順に従います。
  `error` 疑似図種では、要約は `{}` です。
- normalization は、各値を変換した形で読みます。
  その形を得るため、テストのヘルパーが、
  木の範囲をパーサー自身の字句解析器で読み直します。
  このヘルパーは公開 API ではありません。
- 要約に要る字句の判断は、すべてパーサーの単位から取ります。
  文字列の中身がどこにあるか、どの文字列が空か、
  subgraph の名前のどの `click` が `click` の単位か、
  文の最初のスタイルがどこから始まるか、
  そしてクラス図では、名前とスタイルとジェネリクスの型の単位と、
  閉じていないバッククォートの名前がどこで終わるか、です。
  ヘルパーがこれらを独自の規則で決めることはありません。
  単位が誤っていれば、Db が mermaid.js と食い違います。
- パーサーは埋め込みデータを読みません。
  埋め込みデータとは、フロントマターの title、設定、
  各データブロックが設定するものです。
  これらには、同じテキストについて mermaid.js が導いたものを使います
  （`@mmd-toolkit/tests` の `resolveEmbeddedData()`）。
- 木のデータブロックが、mermaid.js の適用したブロックと、
  数・順序・id で一致することを確かめます。
- シーケンス図の box の色の候補が色かどうかは、ブラウザーの答えで、
  テキストにはありません。
  テストは、`@mmd-toolkit/tests` の normalizer が mermaid.js に与えるのと、
  同じ関数（`cssSupportsColor()`）から取ります。

既知の差異が付いた fixture は、仕様の結果を期待します。

## 既知の差異

[既知の差異](../../spec/docs/known-divergences.ja.md)が付いた fixture は、
すべて参照入力でも確かめます。
`comment-takes-character`、`comment-takes-line-break`、
`name-start-reads-unit` では、参照入力の代わりに、
mermaid.js に入力を別の読み方で読ませます。
この確かめは、mermaid.js との違いがその差異だけで説明できることを示します。

- `directive-as-token-boundary`:
  ディレクティブを取り除いた入力をパーサーが読み、
  元の入力に対する mermaid.js の結果と一致すること。
- `html-tag-in-frontmatter`: 元の入力に対するパーサーの結果が、
  フロントマターでタグが始まらないようにした入力に対する、
  mermaid.js の結果と一致すること。
- `click-reserved-word`: パーサーが入力を拒否すること。
  参照入力は、入力からコメント領域と空の形と、
  クリックの文を始めない各 `click` を、
  その click の文脈が読む前後の空白とともに除いたもの。
  パーサーの字句解析器が参照入力を、
  除いたもの以外の入力の単位として読み、
  パーサーが参照入力を受理し、
  それらの `click` の各 click の id のテキストが、
  参照入力の木の 1 つの葉のノードの中にあるなら、
  元の入力に対する mermaid.js の結果と一致すること。
  単位を比べるとき、それらの `click` の click の id は、
  その場所で別の単位として読まれてもよい。
  どの `click` がクリックの文を始めるかは、パーサーの単位から求めます。
- `comment-takes-character`: 入力が、ディレクティブの外に、
  `number` の単位の直後か、
  シーケンス図の字句解析器が文の文脈で規則の一致を始める、
  空白でない文字の直後にある `%%` を持つこと。
  直後かどうかは図のテキストの上で決め、
  単位も、規則が一致を始める位置も、パーサーの字句解析器から取ります。
  mermaid.js には、その差異が名指す字句解析器の 2 つの規則を変えて入力を読ませ
  （`@mmd-toolkit/tests/mermaid` の `withoutDivergences`）、
  パーサーはその結果と同じ受理・拒否と、受理なら同じ Db を与えること。
- `name-start-reads-unit`: 入力が、テキストが `"`、
  `~`（バッククォートの名前のとき）、`<<`、`>>`、
  差異が挙げるキーワードのどれかで始まる、
  バッククォートの名前かジェネリクスの型を持つクラス図であること。
  それは、パーサーの `backquoted` と `generic-text` の単位から求めます。
  mermaid.js には、その差異が名指す字句解析器の規則の順を変えて入力を読ませ、
  パーサーはその結果と同じものを与えること。
- `comment-takes-line-break`: 入力が、
  行の中で単位の後にある図のコメントを持つクラス図であること。
  そのコメントは、パーサーの字句解析器と単位から求めます。
  mermaid.js には、その差異が名指す字句解析器の規則を変えて入力を読ませ、
  パーサーはその結果と同じものを与えること。
- `tokenless-empty-forms`: パーサーが入力を拒否すること。
  参照入力は、入力からコメント領域と空の形を除いたもの。
  空の形とは、空の文字列、空の呼び出し、
  文を始めない空の説明のブロック、
  クラス図ではさらに空のバッククォートの名前と空のジェネリクスの型である。
  パーサーの字句解析器が参照入力を、
  空の形の単位以外の入力の単位として読み、
  パーサーが参照入力を受理するなら、
  元の入力に対する mermaid.js の結果と一致すること。

## 木の不変条件

生成した入力で、
[`ast.md` の不変条件](../../spec/docs/ast.ja.md#不変条件)を確かめる検査があります。
検査は、次のことも確かめます。

- あるノードの子のノードは重ならず、子の欄の順に取るとソース順に並ぶ。
  例外は、2 つの矢印の間にテキストを持つ FlowchartLink で、
  ソースでは `label` が `arrow` の前にある。
- `loc` が `range` と一致する。

flowchart では、
[`ast/flowchart.md`](../../spec/docs/ast/flowchart.ja.md) が木について述べることを確かめます。

- どの葉のノードの値も、その範囲、
  またはノードの種類が決めるその一部のテキストである。
  Identifier の名前は、そのトークンのテキストを順につないだものである。
  文字列の中身がどこにあるかと、行の規則がどの `;` を無視するかは、
  パーサーの字句解析器と単位から取ります。
- 値のトークンは、値のノードの内側にある。
  値のトークンとは、
  `Identifier`、`RawText`、`Numeric`、`String` のトークンである。
- `Keyword` と `Punctuator` のトークンは、データブロックの区切りを除いて、
  値のノードの内側にない。
- ヘッダーの方向は、ヘッダーのキーワードの後の、図の最初のトークンである。
  間にある `Directive` のトークンは、それに当たらない。
- 形の名前は区切りと一致する。
- リンクの各矢印は 1 つのトークンで、その欄は矢印が書くものである。
  欄とは、記号と線と、閉じた矢印では線の文字の数である。
  リンクの開く矢印の線は、閉じる矢印の線と同じである。
- 説明のブロックが閉じているのは、最後のトークンが `}` のときに限る。

シーケンス図では、
[`ast/sequence.md`](../../spec/docs/ast/sequence.ja.md) が木について述べることを確かめます。

- どの葉のノードの値も、その範囲、
  またはノードの種類が決めるその一部のテキストである。
  データブロックでは `@{` と `}` の間のテキスト、
  数では `raw` が書く数である。
  Identifier の名前は、そのトークンのテキストを順につないだものである。
- 値のトークンは値のノードの内側にあり、
  `Keyword` と `Punctuator` のトークンは、データブロックの区切りを除いて、
  値のノードの内側にない。
- ノードの固定の語と演算子は、そのノードのトークンである。
  参加者の文の `create` とキーワード、
  メッセージの活性化と中央の接続、ノートの位置、
  テキストの wrap の接頭辞、autonumber の文の `off`、
  閉じた説明のブロックの `}` である。
- メッセージの矢印は 1 つのトークンで、その欄は矢印が書くものである。
  欄とは、始まりの記号と線と終わりの記号である。
- box のテキストの各部分、色の候補と残りは、それぞれ一つのトークンである。

クラス図では、
[`ast/class.md`](../../spec/docs/ast/class.ja.md) が木について述べることを確かめます。

- どの葉のノードの値も、その範囲、
  またはノードの種類が決めるその一部のテキストである。
  StringLiteral では引用符を除いたテキスト、
  閉じていなければ開く引用符だけを除いたテキスト、
  矢印ではそのトークンのテキストである。
  Identifier の名前は、そのトークンのテキストを順につないだものである。
- 値のトークンは値のノードの内側にあり、
  `Keyword` と `Punctuator` のトークンは値のノードの内側にない。
- 矢印の各関係の端と線は `Punctuator` のトークンで、
  端は線の両側に多くとも 1 つずつである。
  矢印の欄は、それらが書くものである。
- メンバーの可視性と分類子の印は、そのメンバーの `Punctuator` のトークンである。
  可視性の印が最初に来て、分類子の印は多くとも 1 つである。
- 方向の文のキーワードは `direction` とその値で、
  リンクの target はその最後のトークンである。

`error` 疑似図種では、
`Directive` のトークンとフロントマターのトークンを除いて、
ほかのトークンが `RawText` で、
最長の並びであることを確かめます。

- トークンは空白も行終端子も含まない。
- 2 つのトークンが接するのは、一方が `;` のときだけである。
- コメントはすべてトークンの外にある。

この検査そのものにも、壊した木を与えるテストがあります。

## テストがソースから自分で読むもの

検査がソースから事実を自分で読むのは、
その事実をほかに確かめるものがないときだけです。
各ノードの `loc` とコメントの値は、どこでも mermaid.js と比べられないので、
木の検査が、行と列と、コメント行の `%%` と、図のコメントの印を、
ソースから自分で求めます。
文字列、コメント領域、`click` の単位、無視される `;` の読み方は、
値を変え、したがって mermaid.js と比べる Db を変えます。
これらについては、ヘルパーはパーサーの字句解析器と単位を使い、
ソースを別の読み方で読み直しません。

## mermaid.js との差分比較

テストは、`@mmd-toolkit/tests/mutation` を通じて、
`parse()` を pin した mermaid.js と比べます。

- すべての図に共通の規則は、生成した入力で比べます。
  件数は種ごとに 300 です。
  `MMD_DIFFERENTIAL_COUNT=3000 CI=true npx vitest run tests/differential` で、
  テストを書き換えずに件数を増やせます。
  図種と Db の要約が一致しなければなりません。
- flowchart は、fixture の入力を 1 か所だけ編集した変異の入力で比べます。
  件数は fixture ごとに 1 つです。
  `MMD_MUTANTS_PER_FIXTURE=20 CI=true npx vitest run tests/differential/flowchart-mermaid.test.ts`
  で、テストを書き換えずに全件を確かめられます。
  図種と Db の要約が一致しなければなりません。
- シーケンス図も、fixture の変異の入力で同じように比べます
  （`tests/differential/sequence-mermaid.test.ts`）。
  加えて、受理される fixture の入力の 1 文字の後に `%% c` を入れた、
  `comment-takes-character` の入力でも比べます。
  ほかの既知の差異の fixture は、2 つの差異が重なった入力になるので除きます。
  件数は、全体から等間隔に選んだ 300 です。
  `MMD_COMMENT_INPUTS=1000000 CI=true npx vitest run tests/differential/sequence-mermaid.test.ts`
  で、すべてを比べます。
  違いはすべて既知の差異で、下のとおりに説明されなければなりません。
- クラス図も、fixture の変異の入力で同じように比べます
  （`tests/differential/class-mermaid.test.ts`）。
  加えて、受理される fixture の入力にコメントを入れた、
  `comment-takes-line-break` の入力でも比べます。
  各行の終わりと、行の中の各空白の後に ` %% c` を入れたものと、
  各行の後に `%%` か `%%{ }%%` の行を入れたものです。
  件数は、全体から等間隔に選んだ 300 で、
  シーケンス図と同じく `MMD_COMMENT_INPUTS` で増やせます。
  Db が単位の境界でテキストを読む所は、
  そうした文の各位置に、空白、タブ、ディレクティブ、コメントの行を入れて比べます
  （`tests/differential/class-source-reading.test.ts`）。
  その所とは、可視性の印の後の空白、スタイルと名前の単位、
  すべて空白のジェネリクスの型とラベルと注釈の行、
  閉じていないバッククォートの名前です。
  メンバーの行は、クラスの本体とラベルの両方で、
  各位置に空白 1 つ、空白 2 つ、タブを入れて比べます。
  これは、可視性の印の後、`)` の後、分類子の印の前の戻り値の型の後、
  U+2028 と U+2029 の後の空白を、Db が読むからです。

テストのヘルパーが字句の判断を独自の規則で行っていたころに誤った入力も比べます。
木から作った Db が mermaid.js と一致し、木が木の検査を通らなければなりません。

パーサーは既知の差異を区別しないので、差異の申告はテストが行います。
申告した違いは、すべて確かめます。

- ディレクティブによる拒否は、ディレクティブを取り除くとなくなること。
- クリックの文を始めない `click` や空の形による拒否は、
  パーサーが参照入力を受理するなら、
  元の入力に対する mermaid.js の結果と一致すること。
- 両方向の違いは、`html-tag-in-frontmatter` では参照入力に対する、
  `comment-takes-character`、`comment-takes-line-break`、
  `name-start-reads-unit` では、
  差異が名指す字句解析器の規則を変えた入力に対する、
  mermaid.js の結果と一致すること。
- 最初の単位がヘッダーでないクラス図の拒否
  （`headerless-empty-ending`。一方向の差で、参照の読み方はない）は、
  mermaid.js が受理する入力であること。
  ヘッダーがないことは、パーサーの字句解析器が決める。
- 埋め込みデータによる mermaid.js の拒否は、
  仕様が挙げるエラーのどれかであること。

## パースの結果のスナップショット

すべての fixture について、`parse()` の結果をスナップショットとして置きます。
置き場所は、fixture の入力と並べて、
`packages/tests/fixtures/<diagram>/<fixture 名>/` です。

- パーサーが受理する入力では、`ast.json` に木を置きます。
  中身は、位置を含めた `JSON.stringify(root, null, 2)` です。
- パーサーが拒否する入力では、`parse-error.json` に、
  `ParseError` の `message`、`range`、`loc` を置きます
  （`index` は `range` の始まりです）。
  パーサーが拒否を報告する位置の記録です。
  既知の差異では原因の形（[`error-positions.md`](./error-positions.ja.md) を参照）、
  mermaid.js も拒否する入力では、一般の規則が決める位置です。
  拒否も木と同じだけ記録され、
  報告する位置が変わればファイルの変化として現れます。
- fixture は 2 つのうちどちらか一方を持ちます。
  図種にまだ対応していないときは、どちらも持ちません。
  両方を持つ fixture がないことを、ファイルだけを見るテストで確かめます。
- どの木やエラーが変わっても、そのファイルの変化として現れます。
  `packages/parser` で `pnpm run test:update` を走らせると、
  スナップショットのテストだけを `-u` 付きで走らせ、ファイルを書き直します。
- `ast.json` と `parse-error.json` が取り残されていないことを、
  テストで確かめます。
  入力のないフォルダにあるものと、
  もう一方のファイルがあるべきところにあるものです。

### fixture を足した後

`@mmd-toolkit/tests` が足した fixture には、
パーサーのテストを走らせるまで、どちらのファイルもありません。
CI の外では、スナップショットのテストが足りないファイルを書いて通ります。
CI（`CI` が設定されている）では、ファイルがないとテストが失敗します。

そのため、fixture を足した人は次のようにします。

1. `packages/parser` で、スナップショットのテストを 1 回走らせる。
   `pnpm run test tests/parse-result-snapshots.test.ts` である。
2. 新しい `ast.json` と `parse-error.json` を読み、
   木とエラーが仕様どおりであることを確かめる。
3. fixture と一緒にコミットする。

fixture を改名・削除するときは、古いファイルも一緒に動かすか消します。
取り残されたものは、取り残しを探すテストが名前を挙げます。

## そのほかのテスト

- ノード型のコメントにある例を、すべて parse します。
  コメントは `src/ast/flowchart.ts`、`src/ast/sequence.ts`、
  `src/ast/class.ts` にあります。
  `^` が示す範囲を、ノードの範囲と比べます。
- README の「使い方」の例を parse し、示している値と木を結果と比べます。
- 単体テストが、`common.md` の各規則、検出器の表、
  `visitorKeys` と `traverseNodes`、flowchart の木とそのトークン、
  シーケンス図とクラス図の木とそのトークンと文法の外の拒否を扱います。
