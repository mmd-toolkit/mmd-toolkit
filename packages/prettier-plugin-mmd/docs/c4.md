# C4 formatting rules

Japanese version: [c4.ja.md](./c4.ja.md)

How prettier-plugin-mmd formats the five C4 diagram kinds, following the
[C4 syntax](../../spec/docs/diagrams/c4.md) and
[tree](../../spec/docs/ast/c4.md). Each rule keeps what mermaid.js reads; where
several spellings mean the same thing, the rule explains its choice.

Some words used below:

- A **boundary** is a call with children in braces, such as
  `System_Boundary(b, "B") { ... }`; an ordinary call is `Person(a, "A")`.
- An **empty description block** is `accDescr {}` or a description block with
  only whitespace, comments, or directives and no description text. It is not a
  statement separator. Such blocks can also stand between the header and its
  required newline, or between a boundary call and its opening `{`.
- An **argument** is one entry inside call parentheses. It can be **bare**
  (without quotes), quoted, or named (`$descr="D"`), or have no text; its
  position can affect what mermaid.js draws even when it has no text.
- A **directive** is `%%{ ... }%%`; mermaid.js removes it before reading the
  diagram. A **standalone comment** is on a line of its own, and a **trailing
  comment** follows other text on the same line. A **diagram comment** is one
  that the C4 reader handles itself, such as `Person(a, "A") %% note`; it runs
  through U+2028 and U+2029 to LF. Whitespace-only lines after it can decide
  whether the next statement is accepted.
- A **line** ends at LF (CRLF and lone CR are normalized). For the shared
  **semicolon line rule**, U+2028 and U+2029 outside comments and directives are
  boundaries too. The rule can remove a last semicolon where `style` or
  `classDef`, a colon, and a later hash appear in order; see
  [the shared rule](../../spec/docs/common.md#style-and-classdef-lines). A
  **kept part** is text that this printer preserves to keep that rule's reading:
  through the last semicolon on such a line.
- **Exterior whitespace** lies outside a value, comment, or directive, such as
  indentation before `Person` or spaces after its completed call. An **ASCII
  space** is U+0020.

Each section shows input and output from fixed formatting fixtures. Invisible
characters and whitespace at line ends use escaped strings instead, with test or
fixture citations. In those strings `\n` means LF, `\r` CR, `\t` a tab, and
`\u2028` and `\u2029` the Unicode separators; they stand for characters, not
backslashes in a diagram. See
[Documents and fixtures](./development.md#documents-and-fixtures).

## Rules

### Header

The header stands at column one so the start of the diagram is easy to find; its
written kind stays `C4Context`, `C4Container`, `C4Component`, `C4Dynamic`, or
`C4Deployment`. The newline after the header stays after any empty description
blocks, and a trailing comment stays with its following blank or whitespace-only
lines because those lines can decide whether mermaid.js accepts the diagram.

### Indentation

Statements stand one configured indentation step below the header and one more
inside each boundary, and a closing brace aligns with its call, so indentation
shows the nesting. A step follows `tabWidth` and `useTabs` (two spaces by
default); standalone comments and directives align with nearby statements,
including where the line holds a semicolon. Continuation lines inside values
keep their written columns because those spaces can be value text.

### Boundary bodies

The opening `{` follows the call and any empty description blocks after one
space, children start below it, and `}` aligns with the call on its own line,
making nesting visible as in requirement diagrams. This layout also joins a
separately written `{` beside a semicolon line; a Unicode separator, comment, or
directive between the call and `{` keeps the written line break because moving
it can change what mermaid.js reads. A semicolon or an empty description block
can keep a closing brace on the preceding child's line (see the corresponding
rules below).

### Statements one per line

Each statement other than an empty description block gets its own line, so a
description followed by a call is easy to read. Calls, relationships, updates,
repeated aliases, and excess arguments keep their order; empty blocks,
semicolons, and inline directives keep the statements beside them together where
splitting them would change what mermaid.js reads.

### Blank lines

Runs of ordinary blank lines become one, and blank lines at the edges of the
diagram or a boundary body disappear, separating groups without accumulating
empty space; blanks before standalone comments or directives follow the same
rule. A diagram comment keeps all following blank and whitespace-only lines,
including at the end of the file, because removing them can change acceptance;
blank lines inside values stay with that text. Whitespace-only description
interiors print `{}`, because there is no text for whitespace to surround.

### Comments

A standalone comment aligns with the following statement, or the last statement
at the end of the file, and stands at column one before the header, making its
position among the statements clear. A trailing comment stays trailing: a gap
becomes one space, and no gap stays no gap; the lines after a diagram comment
and the kept part of a semicolon line take precedence over this spacing. A `%%`
inside a title or accessibility value remains value text, and comment lines
inside a value keep their written boundaries because moving them can change that
value.

### Argument spacing

Call padding is compact: whitespace after `(` disappears, a comma before a
nonempty argument gets one following space, and ordinary bare arguments lose
exterior whitespace, making lists readable without changing the arguments.
Whitespace that is itself an argument stays, including the spaces between a
closing quote and a comma; a non-ASCII-space prefix before a bare argument
starting with `"` or `$` stays too, because removing it changes the argument's
form. Adjacent arguments, multiline gaps, and inline directives keep their
written separation, and the printer adds no space before `)`.

Bare and quoted arguments keep their written forms, even when mermaid.js reads
them alike, to retain the author's choice. Text inside quotes stays, including
edge spaces, empty strings, backslashes, entities, HTML, and percent text; a
final bare argument keeps its comma because without that comma `)` is still part
of its text.
