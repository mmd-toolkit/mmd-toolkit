# パーサーの性能レビュー

英語版: [SKILL.md](./SKILL.md)

有効な Mermaid 全体、公開パーサーの実測、コードと仕様から、
修正者が事実を確認できる指摘を作る。
有効な入力の遅さは性能の問題であり、構文の失敗は必要ない。

## 範囲とリポジトリの規則

AGENTS.md と [conventions](../conventions/SKILL.md) を読む。
依頼された図の種類と、共通処理を含むかを確認する。
現在の公開 API、振り分け、仕様、fixture、pin した Mermaid の版を調べる。
以前の図種の一覧や実測値を固定して持ち込まない。

この手順の成果物は、レビューの報告と単独の再現コードである。
固定した有効な構文の規模の変更は、
ユーザーが許可した性能の報告・再現の範囲で行い、
パッケージの適合性テストとは分ける。
生成するパッケージのテスト、corpus の追加、ランダムな入力、
任意の構文断片の組合せを許可するものではない。
現在のユーザー指示とリポジトリの制約を優先する。
ファイルの置き場所だけでは例外にならない。
現在のレビューについての許可を使う。
現在のレビューについて既に認められた例外を、再び確認しない。

未確認の probe とログは作業ツリーの外に置く。
確認した報告は依頼された場所、通常は `tmp/review` に書く。
報告の依頼は、製品コードの修正、fixture の変更、commit、
stage の変更の許可ではない。
関連するローカル変更も含め、計測したコードの状態を記録する。
他の作業による編集で、以前の結果が無効になる場合がある。

## 実際の解析経路から候補を探す

図の lexer、grammar、拒否条件の検査と、
そこから呼ぶ共通処理、実装している仕様の規則を読む。
公開 API から前処理、最終的な AST の構築まで追う。
共通処理の範囲を述べる前に、他の呼び出し元も探す。

失敗した残り全体の先読みの後に一文字だけ進んで再試行するか、
文やノードごとに図全体の配列を探すか、
親ごとに子孫すべての字句をコピーするか、
順序付きの範囲を毎回先頭から探すか、既知の境界を越えて探すかを考える。
これらは調査の問いであり、必ず問題があるというチェックリストではない。

候補ごとに、何が増え、何を固定するかを特定する。
長い ID、文の数、深い入れ子、二つの増加する量の積を区別し、
入力全体の長さとの関係を述べる。
仕様や必要な出力そのものが、その処理量を要求するかも確認する。
照合の優先順位だけでは、同じ場所の再走査を要求しない。

## 有効で意味のある再現を作る

疑う経路を通る、小さな完全な図から始める。
その入力を、現在 pin した Mermaid が受理することを確かめる。
変更していない公開 `parse(input)` に渡し、
AST から作った Db と Mermaid の Db を比べる。

計測するすべての規模と比較入力について、正確に同じ完全な入力を使い、
実際の pin した Mermaid の受理と Db の一致を確認してから時間を報告する。
小さな例の成功だけでは、大きい入力を検証したことにならない。

`packages/tests` の現在の補助処理を使う。
例えば `runMermaidWithEmbeddedData`、`dbFromTree` と、
必要な embedded data、browser の代替処理である。
`MMD_TOOLKIT_MERMAID_CACHE=disabled` で保存済みの結果を無効にする。
古い呼び出し方をコピーせず、現在の契約を確認する。
normalizer がない場合や環境による失敗は、検証の限界であり、
一致の成功や構文の拒否ではない。

同じ有効な構文の形を、複数の明記した規模で確認する。
反復処理の原因となる量を変え、二つの量の同時増加が必要なら明記する。
LF だけとスペース入り空白行など、原因の条件を示す比較を使ってもよい。
未確認の比較入力を安全と呼ばない。
規模と計測回数は、解釈できる値と機械の負担から選び、
以前の数を機械的に使わない。

単独の再現コードの中に、すべての完全な入力を
複数行のテンプレートリテラルで直接書く。
通常の図の各行をそのまま見せ、
`\n` escape が並ぶ一行の文字列に圧縮しない。
見えない条件の文字であるスペース、タブ、CR などは、
見える escape で示す。
特定した部分を増やす明示的な `.repeat(...)` は使えるが、
図を読めなくする汎用 builder は使わない。
`input.mmd`、fixture、共有した再現 helper は作らない。
既存の parser や Db 検証の import は使えるが、
再現コード一つで、その入力と計測が分かる形にする。

## 公開 API で図全体を計測する

計測するのは、変更していない公開パーサーの呼び出しだけである。
入力の構築、実際の Mermaid、Db 比較、warm-up、assertion、
sort、ログ出力は計測の外に置く。
内部 helper の直接呼び出し、monkey patch、作業量カウンタ、
任意の操作回数の上限を、図全体の実時間の再現の代わりにしない。

他の agent と調整し、性能計測は順番に実行する。
重い検査と競合させない。
各 sample、中央値、規模間の比、入力全体の UTF-16 長、
増加する量、runtime と Mermaid の版、コマンド、
source か build か、既定でない option を残す。
検証 helper の stack 要件と、パーサーの挙動を区別する。

時間と独立して、コードの反復処理を分析する。
有限の比は漸近計算量の証明ではなく、二倍で厳密に四倍とも限らない。
線形の処理、reader の検索、必要な出力の大きさ、計測の揺れを考慮する。
同じ入力で複数の処理が増える場合、
図全体の時間や比較との差は、個別の関数の時間ではない。

時間の assertion は大きな増加の診断に使えるが、
閾値はすべての環境に対する性能の契約ではない。
失敗させるためだけに閾値を調整したり、不都合な sample を除いたり、
好みの結果になるまで計測を繰り返したりしない。
受理と Db の検査は、性能の診断とは独立して成功する形にする。
実測で遅さを確認できなければ、候補を未確認のまま残し、
完成した指摘にしない。

## 原因ごとに独立して確認できる報告

確認した原因ごとに、内容が分かる一つのディレクトリを作る。

| ファイル             | 内容                           |
| -------------------- | ------------------------------ |
| `report.md`          | 証拠、コード上の原因、修正範囲 |
| `report.ja.md`       | 報告の日本語版                 |
| `reproduce.test.mjs` | 完全な入力、検証、時間計測     |
| `importance.md`      | 修正優先度と理由               |
| `importance.ja.md`   | 優先度評価の日本語版           |

README、総括の報告、入力 fixture、共有のテスト枠組みは追加しない。
複数の図で再現した共通の原因は、同じディレクトリに置く。
似た走査でも、独立した修正が必要なら別の報告にする。

報告には、症状、正確な条件、実測した規模と時間、
実行コマンドと条件、ソースの位置、反復する処理、仕様との関係を書く。
受理、token text、source range、空白、directive、コメント、
関係する判断を保つ、限定した修正の要件を示す。
修正を実装したり、無関係な refactor を提案したりしない。

実行した証拠を **実行**、コードや仕様の証拠を **読取** とし、
未計測の入力を明記する。
共通コードがあることは、すべての図を計測した証拠ではない。
有限の実測を全入力の主張に変えたり、他に問題がないと示唆したりしない。
正しさの不一致が出たら、適用される review の規則で別に分類する。
依頼された性能の調査を、構文の失敗を探す作業に置き換えない。

## 修正優先度を評価する

高、中、低を相対的な修正順として使う。
必要な入力形、起こりやすさ、実測の絶対時間と入力の規模、
確認した範囲から理由を書く。
起こりやすさの判断と利用統計を区別する。
構文が普通でも、数千回の反復や数千段の深さが普通とは限らない。
一方、小さな入力で大きな遅延があることは重く評価する。

空白行の連続と、一行のラベル内の数百のスペースを区別する。
単純な空白と、directive 数も増加する入力も区別する。
共通コードは影響し得る範囲を広げるが、利用頻度の証拠にはならない。
どんな実利用があれば優先度を変えるかを書く。
計測していない editor、formatter、linter の操作時間は主張しない。
優先度が低くても、確認した問題がなくなるわけではない。

## 検証して引き渡す

報告するコードの状態で、最終の単独再現コードを実行する。
実際の結果と、報告するすべての値をログと照合する。
受理と Db の成功を、時間の診断と分ける。
結果が不確かでも、元の sample を残す。
パーサーのコード、入力値、計測処理の変更や、
未解決の懸念が必要とするときだけ再実行する。
一度実際に再現を実行した後の文章や表示だけの変更では、
完全な入力値と計測処理が不変だと確認できれば、計測を繰り返す必要はない。

英日対応、ローカルのソースへのリンク、不可視文字、
日本語の幅、整形を確認する。
検査が `tmp/review` を無視する場合は、
追跡された検査設定を変更せず、報告ファイルを明示的に検査する。
実際の変更に必要な検査を実行し、
報告だけの変更で無関係なパッケージ全体のテストを実行しない。

指摘が一件完成するごとに、報告へのリンクと実行の証拠を簡潔に通知する。
未確認の候補と未計測の範囲を、完成した指摘と分ける。
既存の fixture の成功や、有限の規模の probe が遅くなかったことは、
他の性能問題がないという保証ではない。

## Codex の応答が中断される場合

ユーザーが「このコンテンツは表示できません」という見出しと、
サイバー安全機構や Daybreak に言及する通知を報告したら、
応答の中断として状況を確認する。
パーサーの拒否や、性能テストの失敗として扱わない。
[OpenAI の公式ドキュメント](https://learn.chatgpt.com/docs/cyber-safety#false-positives)
は、正当な作業や無関係な作業でも安全機構が働く場合があると述べている。
ただし、個別の通知の原因や、誤判定であることを確定する証拠ではない。

- 確認できる通知を記録し、直接見たのか、ユーザーから報告されたのかも示す。
  完了した作業と未検証の作業を分ける。
  アカウントの制限や、見えない判定を推測して断定しない。
  ローカルのツールが使えることだけでは、応答が届いたことや、
  作業全体が中断せず続いたことの証拠にならない。
  通知を防げることや、中断せず続けられることを約束しない。
- 完成した報告、元の sample、コマンド、コードの状態、
  最後に検証した手順を残す。
  再開したら、保存済みのファイル、ログの完了状態、
  自分の実行 session、他の agent の計測状況を確認してから再試行する。
  現在の入力とコードを、記録した状態と比較する。
  元の許可されたレビューを続け、未完了の検証は未完了のまま示す。
  部分的な出力を完成した証拠にせず、
  以前の実行が動作中なら同じ計測を重ねて開始しない。
- モデルの変更で通知が消えることや、Daybreak の利用権が得られることを、
  約束しない。
  [利用には別の承認要件がある](https://learn.chatgpt.com/docs/cyber-safety#trusted-access-for-cyber)。
  このスキルは安全機構を回避する方法を提供しない。
  誤判定が疑われる通知で進められない場合は、限界を説明し、
  利用可能でユーザーの役に立つ場合は、公式の `/feedback` 案内を示す。
  ユーザーの許可なく feedback を送信したり、利用申請を出したり、
  報告やログを外部へ送ったりしない。
