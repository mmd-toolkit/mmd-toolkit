# パーサーの性能レビュー

英語版: [SKILL.md](./SKILL.md)

指摘とは、公開パーサーが遅く読む、有効で完全な Mermaid の入力である。
記録した時間と、それを説明するコードと仕様を伴う。
構文の失敗は要らない。

## 範囲

AGENTS.md と [conventions](../conventions/SKILL.md) を読む。
依頼された図の種類と、共通処理を含むかを確かめる。
現在の公開の入口、振り分け、仕様、fixture、pin した Mermaid の版を読む。
以前の図種の一覧や実測値を使い回さない。

成果物は、レビューの報告と単独の再現コードである。
固定した有効な形の規模を変えるのは再現コードの中だけで、パッケージのテスト、
corpus、ランダムな入力、構文断片の組合せには入れない。
製品コードの修正、fixture の変更、commit、stage の変更はしない。

未確認の probe とログは作業ツリーの外に置き、
確認した報告は依頼で指定された場所に書く。
後の編集で結果が無効になりうるので、ローカルの変更も含め、
計測したコードの状態を記録する。

## 実際の解析経路から候補を探す

図の lexer、grammar、拒否条件の検査を、そこから呼ぶ共通処理と、
実装している仕様の規則とともに読む。
公開の入口から前処理を経て最終的な AST まで追う。
疑わしい共通処理の範囲を述べる前に、ほかの呼び出し元を探す。

問うこと: 失敗した残り全体の先読みの後に 1 文字だけ進んで再試行するか、
文やノードごとに図全体の配列を探すか、親ごとに子孫すべての単位をコピーするか、
順序付きの範囲を先頭から探し直すか、既知の境界を越えて探すか。

候補ごとに、何が増え、何が固定かを特定する。
長い ID、多くの文、深い入れ子、積が費用になる 2 つの量のどれかである。
それを入力全体の長さに関係づける。
仕様や必要な出力がその処理量を要求するかを確かめる。
照合の優先順位だけでは、再走査は要求されない。

## 有効な再現を作る

疑う経路を通る、小さな完全な図から始める。
比較入力も含め、計測するすべての規模のすべての正確な入力について、
時間を報告する前に、実際の pin した Mermaid が受理することと、
変更していない公開 `parse(input)` の AST から作った Db が Mermaid の Db
と等しいことを確かめる。

大きい規模でだけパーサーが失敗する場合は、
各正確な入力を実際の Mermaid が受理し、null でない Db を返すことを確かめる。
パースが成功する規模では AST 由来の Db と比べ、
失敗する規模では例外とスタックを記録する。
この失敗は二乗時間の指摘と分けて報告し、
観測した失敗の規模を上限や最小の失敗として示さない。

`packages/tests` の現在の補助処理を使う。
`runMermaidWithEmbeddedData` や `dbFromTree` などを、
それが要る embedded data と browser の代替処理とともに使い、
`MMD_TOOLKIT_MERMAID_CACHE=disabled` を付ける。
現在の契約を読む。
normalizer がないこと、環境による失敗、
対象パーサーを呼ぶ前の実際の Mermaid のリソース不足の例外は、検証の限界である。
一致の成功でも、パーサーの失敗でも、構文の拒否でもない。
実行していない規模を確かめたと報告しない。

1 つの有効な形を、複数の明記した規模で使う。
反復処理の原因となる量を変え、2 つの量を一緒に増やす必要があれば明記する。
LF だけの空行とスペース入りの空行のように、比較入力で原因の条件を示してよい。
試していない別の形を安全と呼ばない。
規模と計測回数は、解釈できる結果と機械の負担から選ぶ。

単独の再現コードでは、すべての完全な入力を複数行のテンプレートリテラルで、
図の 1 行を 1 行として書く。
見える escape は、見えない条件の文字（スペース、タブ、CR）にだけ使う。
特定した部分は `.repeat(...)` で増やしてよいが、
図を隠す汎用の builder は使わない。
`input.mmd`、fixture のファイル、共有の再現 helper は作らない。
既存の parser と Db 検証の import は使ってよい。
再現コードは、それぞれ自分の入力と計測を説明する。

## 公開 API で図全体を計測する

計測するのは、変更していない公開パーサーの呼び出しだけである。
入力の構築、実際の Mermaid、Db 比較、warm-up、assertion、sort、
ログ出力は計測の外に置く。
内部 helper の呼び出し、monkey patch、作業量カウンタ、操作回数の上限で代えない。

計測は 1 つずつ、マシンでほかの重い検査が動いていないときに行う。
各 sample、中央値、規模間の比、入力全体の UTF-16 長、増加する量、
runtime と pin した Mermaid の版、コマンド、source か build か、
既定でない option を残す。
検証 helper の stack 要件と、パーサーの挙動を分ける。
検証の option を設定しただけでは、API がそれを適用することも、
受理にそれが必要だったことも示さない。
どちらも、その経路を確かめてから主張する。

時間とは独立に、コードの反復処理を分析する。
有限の比は漸近の証明ではなく、入力が 2 倍で 4 倍になるとも限らない。
線形の処理、reader の検索、出力の大きさ、計測の揺れを考える。
同じ入力で複数の処理が増えるとき、図全体の時間やその差は、
個別の関数の時間ではない。

二乗の根拠が collection の一括操作の反復にあるときは、
計測した runtime での挙動を確かめ、その証拠を **読取** とする。
費用の成分を確かめても、その単独の時間や、それが支配的であることは示さない。

時間の assertion は大きな増加を示せるが、閾値は性能の契約ではない。
失敗させるために閾値を調整したり、sample を除いたり、
好みの結果になるまで計り直したりしない。
受理と Db の検査は、時間とは独立に通る。
遅さを確かめられなければ、候補を未確認のまま残す。

## 原因ごとに 1 つの指摘

確認した原因ごとに、内容が分かる一つのディレクトリを作る。

| ファイル             | 内容                           |
| -------------------- | ------------------------------ |
| `report.md`          | 証拠、コード上の原因、修正範囲 |
| `report.ja.md`       | 報告の日本語版                 |
| `reproduce.test.mjs` | 完全な入力、検証、時間計測     |
| `importance.md`      | 修正優先度と理由               |
| `importance.ja.md`   | 優先度評価の日本語版           |

README、総括の報告、入力 fixture、共有のテスト枠組みは作らない。
複数の図で再現した 1 つの原因は 1 つのディレクトリにし、
別々の修正が要る似た走査は別のディレクトリにする。

報告には、症状、正確な条件、実測した規模と時間、コマンドと条件、ソースの位置、
反復する処理、仕様との関係を書く。
要る修正を、受理、token text、source range、空白、directive、コメント、
そのほかの関係する判断を保つ範囲で述べ、実装も無関係な refactor の提案もしない。

冒頭には、遅いと計測した有効な形、増やした量、実測の遅延を書く。
小さな受理例は、遅さの再現ではなく縮小例だと明示する。
再現コードの冒頭コメントは、計測のコードより前に、繰り返す処理と、
比較で変える部分を示す。

実行したと示す例は、空白も含めて試した入力と同じにする。

実行した証拠を **実行**、コードと仕様の証拠を **読取** とし、
計測していない場合を挙げる。
共通のコードは、すべての図での計測した挙動を示さない。
有限の計測をすべての入力に広げたり、ほかに問題がないと示唆したりしない。
正しさの食い違いは review の規則で別に分類し、性能の調査の代わりにしない。

## 修正優先度を評価する

高、中、低を相対的な修正順として、必要な入力の形、起こりやすさ、
実測の絶対時間と入力の規模、確認した範囲から決める。
起こりやすさの判断と利用統計を分ける。
構文が普通でも、数千回の反復や数千段の入れ子が普通になるわけではない。
小さな入力で大きな遅延があれば重く見る。

空行の連続と一行の中の数百のスペースを分け、単純な空白と、
directive の数も増える空白を分ける。
共通のコードは影響しうる範囲を広げるが、利用頻度は示さない。
どんな実利用があれば優先度が変わるかを書く。
計測していない editor、formatter、linter の時間は主張しない。
優先度が低い指摘も報告する。

## 検証して引き渡す

再レビューでは、各指摘を、修正が持ち込んだもの、前からあって見落としたもの、
新しい範囲に分け、見落としなら、前のレビューが扱わなかった場合か経路を挙げる。
前の再現が手に入らなければ、同じ経路の現在の入力を新しい probe とする。
修正を読むことと計測することを分け、遅くならなかった結果は計測した規模に限る。

最終の再現コードを報告するコードの状態で実行し、
結果と報告するすべての値をログと照合する。
受理と Db の結果を時間の診断と分け、元の sample を残す。
再実行は、パーサーのコード、入力値、計測処理を変えたときと、
未解決の懸念があるときだけにする。
入力と計測処理が変わっていないと確かめれば、文章だけの変更で再実行は要らない。

英日対応、ローカルのソースへのリンク、不可視文字、日本語の幅、整形を確かめる。
検査が報告の置き場所を飛ばすときは、追跡された検査設定を変えずに、
報告ファイルを明示的に検査する。
変更に要る検査だけを実行する。

指摘は完成するごとに、リンクと実行の証拠を添えて報告し、
未確認の候補と未計測の範囲をそれと分ける。

## Codex の応答が中断される場合

「このコンテンツは表示できません」という見出しで、
サイバー安全機構や Daybreak に触れる通知は、応答の中断である。
パーサーの拒否でもテストの失敗でもない。
[OpenAI の文書](https://learn.chatgpt.com/docs/cyber-safety#false-positives)
は正当な作業でも安全機構が働くと述べているが、個別の通知の原因は示さない。

- 通知と、それを直接見たか報告されたかを記録する。
  完了したものと未検証のものを分ける。
  原因を述べたり、
  モデルの変更や
  [利用の申請](https://learn.chatgpt.com/docs/cyber-safety#trusted-access-for-cyber)
  で消えると述べたりしない。
- 完成した報告、元の sample、コマンド、コードの状態、最後に検証した手順を残す。
  再開したら、保存したファイル、ログの完了状態、
  まだ動いている計測を確かめてから再試行する。
  現在の入力とコードを記録した状態と比べ、
  未完了の検証を未完了と示してレビューを続ける。
  部分的な出力は証拠ではない。
  同じ計測が動いている間は、それを始めない。
- 安全機構を回避しようとしない。
  誤判定が疑われる通知で進めないときは、限界を説明し、
  公式の `/feedback` の案内を示す。
  ユーザーの許可なく、feedback の送信、利用の申請、
  報告やログのアップロードをしない。
