# 変更の review

## 方針と基準

review は、変更が pin した mermaid.js と仕様に対して正しいか、あるべき形か、
文書が決まりに従っているかを、根拠つきで述べる。
述べるのは 1 回である。
review する者は最初の 1 回ですべての観点を見て、
2 回目には直しが新しく作ったものだけが見つかる状態にする。
最初の回で見つけられたはずのものが再 review で見つかったら、
それは最初の回の失敗であり、報告にそう書く。

review のすべての主張は、実行（mermaid.js、`parse()`、テスト、
計測を自分で動かした）か読解（コードや文書を読んだ）かの印を持つ。
review の対象の報告に書かれた主張は、自分で実行するまでどちらでもない。
数は送る前に数え直す。
数え違いは review 自身への指摘である。

review する者は作業ツリーを編集しない。
probe、写し、生成した入力は作業ツリーの外に置く。

## 1. 範囲

- 変更が触ったすべてのファイルを、報告が指す部分でなく全体を読む。
  複数の図種を扱う文書は、すべての図種について読む。
- 変更が触ったファイルの外で影響しうるものを挙げる。
  変えた共有インターフェースを使うパッケージ、変えた規則を裏づける fixture、
  変えたノードを読む printer と規則。
- 見る前に、この review が見る観点を書き出す。
  mermaid.js に対する振る舞い、各文の場合、あるべき形、文書、依頼者が挙げた点。
  報告には、見た観点と見ていない観点を書く。

## 2. 入力

パーサー、printer、規則の review は、入力で閉じる。
入力は 1 件ずつ mermaid.js と比べる（受理、Db、
フォーマッターなら冪等性と整形後の Db）。
mermaid の事実は、review の対象の実装とは独立に定める。
実装を動かしてその答えを読み返す形では定めない。

入力は文から取る。
変更が関わるすべての文（仕様、parser のトークンと位置の文書、
`dbFromTree` の文書、整形の規則）について、その文が分ける場合と、
その文が名指す場所で接するほかの規則を挙げ、それぞれに fixture があるかを見る。
fixture のない場合は fixture への指摘、文が述べていない場合は文への指摘。
この一覧は 1 回目に、実装を読む前に、すべての場合について書く。
報告には、作者の場合の表（conventions の skill が作者に求める）と並べて載せ、
2 つを突き合わせる。
どちらにもなかった場合が、review 自身の寄与である。
場所と文字列の積は作らない。
積は 1 つの規則を文脈の数だけ繰り返すだけで、問いの名前を持たない。

次の形は、各文で考えるべきほかの規則の一覧である。
省く形があれば、どれをなぜ省いたかを書く。

- 行の終わり（すべての文の形の後）: ` ;`、`;`、`;;`、`; ;`、`: `、終わりの空白、
  終わりのタブ、終わりのコメント、
  終わりのディレクティブ（閉じたものと閉じていないもの）、空行、`\r\n`、
  行終端子のないテキストの終わり。
- 行の規則が無視する `;`: 1 つ、2 つ、3 つを、後ろの空白のありなしで、
  mermaid.js が区切りまで読むすべての値（`style`、`classDef`、`linkStyle`、
  title、説明、ノート）に。
  行の規則は `style` の文に限らず、`style` と `:#` を含むどの行にも効くので、
  その引き金（`style:#x;`、`#x;;  `）をラベル、title、メッセージ、ノート、
  別名の説明にも差し込む。
- 値の中と語の中のディレクティブ（`e%%{init: {}}%%nd`）、キーワードと値の間、
  行の終わり。
  キーワードと値の間には、コメントの行と空行も挟む（`title`、改行、`%% c`、
  改行、`x`）。
- テストか review 自身の入力で、乱数や数（seed、count、
  N 件の標本）で選んだ入力があれば、指摘（重）にする。
  そのような入力を名指す文はなく、回しても問いに答えない。
- フォーマッターが実際に行う変形を入力に施し、mermaid.js と照らす。
  `;` と改行の入れ替え、行末の空白の除去、行の内容を前後の行へ移す、
  2 行をつなぐ、トークンの間の空白をまとめる。
- 共有の関数の変更では、変更の動機になった場所だけでなく、
  それを呼ぶすべての場所での入力。
- lint の規則では、主張ごとに別の入力で確かめる。
  メッセージが「このテキストは何をするか」と言う主張は、
  ちょうどそのテキストだけを取り除いて Db を比べる。
  提案の主張は、
  ちょうど提案の編集を当てて（行を消す提案は行終端子も消す） Db を比べる。
  2 つを 1 つの入力で混ぜると、提案の効果をメッセージのものと取り違える。

入力を組み立てる前に、部品を確かめる。
差し込む文字列が、その名前のとおりのものであること。
部品だけを parse して結果を読む（「閉じたディレクティブ」は `closed: true`、
「コメント行」は 1 つの `Comment`、「行区切り」は U+2028）。
名前と違う部品は、その上に作った結果のすべてを別のものについての主張にし、
review はそれに気づかない。

実装と mermaid.js が食い違った入力は、既知の差異を除くまで指摘にしない。
差を除いた入力（`withoutDivergences`）で mermaid.js を動かし直し、
宣言された差で違いの説明がつくかを確かめる。
この手順がないと、宣言済みの入力を指摘と誤るか、本物の指摘を宣言済みと見逃す。

変更が直しのときは、同じ入力を直す前の版でも回す。
出力の違いは、振り分ける決め方でなく 1 件ずつ読んで、すべて分類する。
直しが意図したもの、直しが報告していない結果、無関係なもの。
報告されていない結果は指摘である。

道具や基盤のコード（mermaid.js の結果の貯蔵庫、fixture の道具、CLI）では、
入力が違う。
その一覧は次のとおり。

- ソースからだけでなく、build（`lib/`）からも動かす。
  build が export しないモジュールは、そこでしか失敗しない。
- 環境を変える。
  タイムゾーン、ロケール、プロセスの順序、複数のプロセス。
  読み戻した結果は、作り直した結果と等しくなければならない。
- ファイルを壊す。
  全バイトで 1 ビットずつ反転、全長で切り詰め。
  壊れたファイルは「ない」として読まれ、別の結果として読まれてはならない。
- 決めた数のプロセスでの並行、日をまたぐ時計、
  死んだプロセスが残したロックや PID のファイル、
  ロックを作ってから中身を書くまでの窓、
  プロセスを起こせない起動（`ulimit -u 1`）。
- 公開の関数の options を、
  直列化すると同じになる形で渡す（`undefined` の欄と欄がない形、
  `NaN` と `null`）。
  結果を変える 2 つの options が、同じ鍵を持ってはならない。

## 3. 文書

- 変えたすべての Markdown 文書に `.ja.md` の対があり、同じ変更で直されていて、
  見出しとコードブロックの数が一致する。
- 変えたすべての日本語の文書について、すべての行の幅を測る。
  検査の出力は絞らない（`grep -v` に通さない）。
  散文の行は 80 桁以内で、全角は 2 桁と数える。
  表、コードブロック、1 つのリンクだけの行は対象外。
- 不可視文字を実際の文字として書かない。
  mermaid.js のソースへのリンクは pin したコミットのパーマリンク。
  Mermaid のコードブロックは info string が `mmd` で、書き方を示す例を除き、
  フォーマッターが印字する形。
- 残す文書は作業の体制に触れない。
  誰が何を担当するか、どこでやり取りするか、作業用のファイルを書かない。
- 文書の主張は、振る舞いを述べるものは mermaid.js で、
  コードが何をするかを述べるものはコードで確かめる。

## 4. あるべき形

振る舞いが正しいときも、すべての review にあるべき形の節を置く。

- それは必要か。
  それが何であるかを表す名前か。
- 1 つの判断が 1 か所にあるか。
  printer と parser に写された規則、呼び出す側ごとに繰り返された条件は指摘。
- 呼ぶ側が、呼ばれる側の述べていない約束（範囲の前に必ずトークンがある、
  欄が必ず空でない）に頼っていないか。
  テストだけが守る約束は、述べられていない。
- 仕様が直接の規則を述べる所で、
  コードが mermaid.js のパイプラインを再現していないか。
- 読みやすさ。
  値からの型の推論、使い手が 1 つの汎用化、読み手のいない間接化、空の JSDoc、
  自動修正の雛形、コメントアウトされたコード。
- 性能の直しでは、速さのための構造に、その場で理由のコメントがあるか。
  飛ばすかたどるかの判断が 1 か所にあり、
  呼ぶ側に書かれていない約束を残していないか。
  名前が役割を表すか。
  添字の計算や状態のフラグが散っていないか。
  速くなっても、前より読みにくくなった所がないか。
  直した人の報告に、読みやすさのために選んだ形と退けた速い形があるか。
- いちばん素直な書き方か。
  読む前に、プロジェクトの対象環境（package.json の `engines`、
  tsconfig.json の `target` と `lib`、依存の版）を確かめ、
  変更された各行を「そこで、より標準的で短い書き方がないか」と問いながら読む。
  実行環境より古い設定（`engines` が動かすものより古い `lib`）は、
  それ自体が指摘。
  これはパターンの表ではなく読み方である（`runs.toReversed()` が使えるのに
  `[...runs].reverse()` と書く、など）。

## 5. 指摘と報告

- review 1 回につき報告は 1 つで、
  すべての指摘を重さつきで載せる（Db や受理の誤り、冪等性の崩れ、
  文書の誤った主張は重。言い回し、行幅、名前は軽）。
  軽い指摘を次の回に取っておかない。
- 各指摘は根拠（入力、mermaid.js の出力、ファイルと行）を持ち、種類を挙げる。
  同じ誤りが現れるほかの場所、図種、形を、直しを提案する前に列挙する。
  種類のない指摘は、1 点だけの直しを招く。
- 再 review では、新しい指摘ごとに出どころを書く。
  直しが作った、前からあって前回見落とした、範囲が新しい。
  見落としには、前回の review が挙げなかった場合か読まなかった所を書き、
  その穴を以後のすべての review の入力に足す。
  前回見つけた場合の隣の場合（同じ文で、同じ区別の別の値。もう一方の行終端子、
  閉じないディレクティブで見つけたなら閉じたもの、
  次の図種）への指摘は見落としであって、範囲が新しいのではない。
  1 回目はその文のすべての場合を挙げるためにあった。
- 同じ項目が 3 回目で新しい指摘を出したら、review は止まり、
  何かを直す前に出どころを報告する。
- parser か仕様への指摘で、入力が適合コーパスにないものには、
  足す fixture を書く。
  その入力はコーパス（`packages/tests/fixtures/`）に残す。
  どの言語の parser も、そこで確かめられる。
  parser の中の一覧には残さない。
- 報告には、見なかったものとその理由を書き、
  誰も通過を網羅的と読まないようにする。

## 6. 機械での実行

- 並列の実行の前に、子プロセスを含めた同時のプロセス数を決める（8〜16）。
  システムの上限を試さない。
  ユーザーごとのプロセス数の上限に当たると、機械のほかの実行が落ちる。
- mermaid.js を動かすコードの写しは、
  結果の貯蔵庫を切って動かす（`MMD_TOOLKIT_MERMAID_CACHE=disabled`）。
  写しが木の `packages/tests` そのものを読み、鍵を共有するときは除く。
- 止めるのは自分のタスクだけで、タスク id か PID による。
  名前でプロセスを止めない。
- ほかの長い実行が動いている間に長い実行を始めない。
  負荷は両方を遅くする。
