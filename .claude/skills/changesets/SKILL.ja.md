# Changesets

`@mmd-toolkit/ast`、`@mmd-toolkit/parser`、`prettier-plugin-mmd`、`mmdfmt`、
`@mmd-toolkit/eslint-plugin`、`@mmd-toolkit/textmate-grammar` は、
Changesets で `main` から公開する（CONTRIBUTING.md の Releases）。
`@mmd-toolkit/ast` と `@mmd-toolkit/parser` は、
`.changeset/config.json` の `fixed` の組である。
片方を上げると、もう片方も同じ版に上がるので、
changeset は変えたパッケージだけを書く。
仕様の `@mmd-toolkit/spec` は npm に公開しないが、同じ仕組みでリリースする。
リリースで、版と変更履歴の項目と、git のタグ `@mmd-toolkit/spec@<版>` が付く。
実装が、従っている仕様の版を名指し、
そこから何が変わったかを読めるようにするためである。
この 7 つへの変更は、同じプルリクエストに changeset を含める。
無いと、その変更は次の版の changelog と版の更新から漏れる。

## changeset が要るとき

- 公開するパッケージの振る舞いが変わるとき。
  parser が受理するものや木に置くもの、フォーマッターが印字するもの、
  lint の規則が報告するものや修正するもの、メッセージ、規則の追加や削除、
  オプション、export する型や関数、文法が単位を何として色付けするか、スコープ、
  文法が従う仕様の版。
- `packages/spec` を変えるときは、常に要る。
- 要らないもの。
  テスト、fixture、リポジトリの文書やスキル、道具、CI だけの変更。
  版を持たない private のパッケージだけの変更も要らない。
  `tests`、`docs`、`playground` がそれで、
  `.changeset/config.json` の `ignore` に並べてある。

プルリクエストの前に `pnpm exec changeset status --since=origin/main`
を実行する。
ブランチの changeset による版の上げ方を一覧にする。
失敗するのは、
ブランチでパッケージを変えたのに changeset が 1 つも無いときだけで、
変えたパッケージそれぞれに changeset があるかは確かめない。
そのため、一覧を、ブランチで変えたパッケージと突き合わせる。
読むのはステージ済みか commit 済みの changeset で、未追跡のファイルは見ない。

## 書き方

`.changeset/<短い kebab-case の名前>.md` を 1 つ置く。

```md
---
"prettier-plugin-mmd": minor
---

Print a one-line `@{ ... }` with one space inside each end: `A@{shape: rect}`
becomes `A@{ shape: rect }`.
```

本文はそのまま、
front matter のすべてのパッケージの changelog とリリースのプルリクエストに載る。
利用者は、それを読んで更新するかを決める。

1 つの changeset に入れるもの。

- 利用者が一言で呼べる変更を 1 つ。
  プルリクエストに変更が複数あれば、changeset も 1 つずつ置く。
  同じ形の変更が複数の図種に及ぶものは、1 つの変更である。
- パッケージを 1 つと、その版の上げ方。
  変更が複数のパッケージに及ぶなら、パッケージごとに changeset を置き、
  そのパッケージの利用者にとって何が変わるかを書く。
  別のパッケージの話は、その利用者の役に立たない。
  `fixed` のグループでは、変わったパッケージだけを名指す。
  依存の新しい版を受け取るだけのパッケージには要らない。
  その更新は changelog に載る。
- リリース前の変更の項目は 1 つ。
  後の変更がそれを広げるなら、2 つ目を足さず、`.changeset/` のファイルを直す。

読みやすさ。

- 2 文までにする。
  1 文目は、何が変わるかを動詞（`Print`、`Report`、`Accept`、`Fix`）で始める。
  2 文目は、要るときだけ、利用者がすることを書く。
  項目は、書くことを削って短くする。
  セミコロンやコンマで文をつないで、文の数を合わせない。
- フォーマッターの印字が変わるなら、変更前と変更後の例を 1 つ示す。
  ある文字列には引用符を付け、別の文字列からは外すように、
  両方の向きがある変更では、向きごとに 1 つ示す。
  lint ルールの報告が変わるなら、ルールを名指し、報告する形を 1 つ示す。
- 公開した版の決定を覆す印字の変更では、1 文目の後に 2 文を足す。
  覆すとは、ある入力を意図して印字していた形を、別の形に変えることである。
  足す 1 文目には、前の規則が何をなぜしていたかと、利用者から見た欠点を書く。
  足す 2 文目には、新しい規則が欠点をどう直し、目的をどう残すかを書く。
  残す場合を名指すのは 1 つまでにする（例: `such as a text with a comma`）。
  そうした項目は 3 文、利用者がすることを書けば 4 文になる。
- そうした変更では、覆す決定を入れた公開済みの版を名指す。
  名指すのは、その版がパッケージの最初の版より後の版のときである。
  例は `which 0.5.0 began to print without the space` である。
- その版が印字を変えていて、新しい変更がその印字を逆の向きに戻すときは、
  パッケージの `CHANGELOG.md` のその版の項目にも、注記を足す。
  たとえば、0.5.0 がコンマの後の空白を取り、
  新しい変更がその空白を戻すときである。
  注記は、項目の文の後に、同じ字下げで、引用として書く。
  引用にするのは、その版がしたことの文と読まれないようにするためである。
  1 行目は `**NOTE:**` と、行を切る `\` である。
  続けて、句 `Overturned in the next release: ` と、
  いま何が印字されるかの 1 文を書く。

  ```md
  > **NOTE:**\
  > Overturned in the next release: the comma of a note is printed with one
  > space after it, as in `Note over A, B`.
  ```

  GitHub は、リストの項目の中の `> [!NOTE]` を、注記の枠として描かない。
  項目は、どれもリストの項目である。
  注記は、その項目を読む人に、項目の変更が後で逆に戻されたことを知らせる。
  後の変更の履歴を書くものではない。
  前の版が形を書かれたまま残していて、
  新しい変更がそれを 1 つの形にそろえるときは、注記を足さない。
  新しい変更が、前の版の変更を同じ向きに広げるときと、
  前の版の形を 3 つ目の形に置き換えるときも、足さない。
  パッケージの最初の版の項目にも、足さない。
  最初の版は、何も変えていない。
  `version:ci` が、この句の `the next release` を、版の番号に置き換える。
  番号は、Changesets がそのパッケージに付ける版である。
  置き換えるのは `scripts/stamp-overturned-notes.mjs` である。
  そのため、changeset は、その `CHANGELOG.md` のパッケージの版を上げること。
  すでに公開された版が変更を逆に戻していた場合は、その版をそのまま書く。

- 変わらない形、規則の条件、規則の裏付けの数は書かない。
  裏付けの数とは、mermaid.js の文書がそれぞれの形を何回書くか、などである。
  それらは規則の文書にある。
  利用者が不具合と思うものや、対応が要るものだけを名指す。
- パッケージの利用者の言葉を使う。
  規則の文書や仕様の語（`Db`、kept line、木）と、別の図種との比較は、
  利用者の役に立たない。
  実装や review の経緯は書かず、理由は、利用者が動けるときと、
  公開した版の決定を覆す変更のときだけ書く。
- 利用者のコードが動かなくなる変更は、そのコードをどう直すかを先に書く。
- 関わる規則、オプション、図種はコードスパンで名指す。
  仕様では、利用者は実装である。
  変わった図種と節を名指す。

版の上げ方。
公開するパッケージでは、`patch` は、
パッケージがすでに謳っていたとおりに動くようにする修正。
`minor` は、利用者が気づく振る舞い、規則・報告・修正・export の追加。
`major` は、1.0 以降に公開 API を壊す変更。
仕様では、版が 1.0 より前のあいだ、`minor` は、実装が従わなければならない変更。
受理するもの、読み方、木、図種の判定、図種の追加や削除がこれに当たる。
`patch` は、それ以外の変更（言い回し、例、リンク、fixture の引用）。

プルリクエストの前に、`.changeset/` のファイルをパッケージごとにまとめて、
changelog に載る形で、この節に照らして読む。
ほかと重なる項目はまとめ、2 つの変更を持つ項目は分け、
上の決まりを外れる項目は書き直す。
