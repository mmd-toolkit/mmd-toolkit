# Conventions for code and documents

These conventions hold in every package. AGENTS.md states each of them in one
line and names the check that enforces it; this document holds the full text.
The procedures of a package are in the skill of that package.

## Code

- No regular expressions in `packages/parser` and
  `packages/prettier-plugin-mmd`, in source and tests alike. The parser matches
  character by character on code points, and its tests state expectations with
  string comparisons. Elsewhere (`packages/tests`, `tools/`, `scripts/`), prefer
  string methods; a regular expression that is still needed carries the `u` flag
  and never the `i` flag (the ESLint rule `regexp/require-unicode-regexp` checks
  the former).
- Leave no empty JSDoc, no stubs generated by autofix, no meaningless comments,
  no commented-out code. Always read the result of an autofix such as
  `eslint --fix`. Known dangerous autofix: `regexp/no-missing-g-flag` rewrites
  `new RegExp(re)` to `new RegExp(re, "g")` and drops the original flags
  (`new RegExp(re.source, re.flags)` is not reported).
- Never put invisible characters (U+2028, U+2029, U+00A0, U+FEFF, control
  characters) literally into source or documents; write escapes, and check the
  bytes after writing. The fixtures of the conformance corpus
  (`packages/tests/fixtures/`) that need the real characters are the only
  exception. A test of the formatter or of the linter that needs such a
  character writes it as an escape, in the test code or in a JSON fixture, and
  not literally in a fixture file.

## Documents

- When a document refers to mermaid.js source code, it links to the exact lines
  on GitHub with a commit-hash permalink of the pinned version
  (`https://github.com/mermaid-js/mermaid/blob/<commit>/packages/mermaid/src/<path>#L<from>-L<to>`),
  with the function or file name as the link text. Bare file names or function
  names without such a link are not enough. The pinned commit is recorded once
  in `packages/spec/docs/index.md`. `pnpm run lint:docs` fails when a link to
  mermaid.js in a Markdown document points anywhere else.
- Every Markdown document in the repository (READMEs, everything under
  `packages/spec/docs/`, this document) is written in English, with a Japanese
  version of the same content next to it as `<name>.ja.md`. Both are updated in
  the same change: a change to an English document is not done until the
  `.ja.md` carries the same change. `pnpm run lint:docs` (part of
  `pnpm run lint` and CI) fails when a document has no pair. Generated tool
  files such as `.changeset/README.md` are exempt; `scripts/markdown-files.mjs`
  lists what the check covers.
- Prose in Markdown documents is wrapped at 80 columns by Prettier
  (`proseWrap: "always"` in `prettier.config.js`). Run `pnpm run format` after
  editing a document; `pnpm run format:check` fails otherwise. Do not write a
  check or a test that depends on where a line of prose breaks. Tables and code
  blocks are not wrapped, so keep table cells short and put long explanations
  below the table. Prettier does not wrap Japanese text, which has no
  whitespace, so it keeps the line breaks of the Japanese documents as written
  (`proseWrap: "preserve"` for `*.ja.md`), and their author writes the line
  breaks: one sentence on a line, and a long sentence broken after a `、` where
  the meaning pauses, so that no line of prose is longer than 80 columns,
  counting a full-width character as two.
- A code block that holds Mermaid text has the info string `mmd`, not `mermaid`
  and not `text`. GitHub highlights it and does not try to render it as a
  diagram, which matters because many examples are rejected or are edge cases on
  purpose. Whitespace at the end of a line does not survive in a code block, so
  an example that needs it is described in a sentence instead. A Mermaid example
  is written as the formatter of this project prints it (indentation, spacing
  around arrows), unless the example is there to show a way of writing: an input
  of the formatter, or text whose spacing is the point. An example taken from a
  fixture is the formatted form of the fixture's input; formatting does not
  change the Db, so the fixture still records what mermaid.js does with it.

## Running tests

The tests of a package take minutes, and several pieces of work share one
machine. Run what a change can affect, not everything after every change.

- A change to documents only (Markdown, comments): run the document checks
  (`pnpm run lint:docs`, `pnpm run lint:chars`, `pnpm run format:check`), and,
  for a changed comment, ESLint on the changed files (`npx eslint <files>`),
  whose rules also read comments. Run no tests, except a test that reads the
  changed document; the skill of the package says which tests read documents.
- A change to code, while working on it: run the test files that the change can
  affect (`vitest run <files>`). The skill of the package says which test files
  go with which part of the code.
- Before reporting the work as done: run the whole suite of the package once,
  and the checks of the repository (`pnpm run lint`, `pnpm run format:check`).
- The tests of a package run fixed inputs only: the fixtures of the corpus, the
  fixtures of the package, and the inputs of past failures. No test generates
  its inputs, and no command does.
- The tests of the parser and of the formatter do not run mermaid.js. A claim
  about what mermaid.js reads is checked against the Db that the corpus records
  for the fixture. The Db of a tree is built by `dbFromTree` of
  `packages/tests`, which the corpus checks against mermaid.js; the formatter
  compares the Db built from the tree before and after formatting (for a corpus
  input, with the recorded Db). mermaid.js runs in the corpus checks only.
- The linter tests do not run mermaid.js. They check the reports and suggestion
  outputs on rule fixtures and document examples. Inputs that need invisible
  characters use ESLint's `RuleTester`, with template literals and escapes for
  the input and expected output in the test source.
- The tests of the parser run no generated inputs and do not run mermaid.js.
  What a parser must do is stated by the specification and by the conformance
  corpus (`packages/tests/fixtures/`): an input, whether mermaid.js accepts it,
  and what mermaid.js reads. A parser in any language is checked with the same
  fixtures, so the tests of the parser take their inputs and their expected
  results from the corpus. A check of the corpus itself (that what a fixture
  records is what mermaid.js does) belongs to `packages/tests`.
- The inputs that check a behavior are fixtures, and every fixture answers a
  sentence. Every sentence that defines a behavior (in the specification, in the
  parser's documents of tokens and positions, in the documents of `dbFromTree`,
  in the formatting rules) has a fixture for each case it distinguishes, and for
  each other rule that meets it at the place it names: a directive, an ignored
  `;`, a comment line, an empty line, a line separator (U+2028, U+2029), an
  empty description block, and whatever else the sentence's own words name. The
  fixtures are written with the sentence, checked against mermaid.js once, and
  cited by the sentence (`[fixture: ...]`). A failure found anywhere is closed
  by a fixture in the corpus (or a formatting fixture) and by the sentence that
  was missing. An input kept only in a list inside a package is not kept.
  Products of places and strings are not written: a product repeats one rule as
  many times as it has contexts and names no question; the cases of a sentence
  are finite and each is named. No input of a test or a review is chosen by a
  random source or by a number (a seed, a count, a sample). `Math.random` is
  reported by the lint; a hand-written generator is caught in review.
- A result that was just reported for the same state of the tree is not run
  again by someone else; a check of another kind (other inputs, another method)
  is.
- The report says what was run and what was not.
- A report of a change in behavior (acceptance, the tree, the Db, formatting, a
  rule) goes to review with a table of its cases: for each sentence the change
  concerns, every case the sentence distinguishes, the fixture that holds it,
  and the mermaid.js result the fixture records. The reviewer reads the sentence
  for cases the table lacks; without the table the review enumerates the cases
  itself and a round is spent on what the author already knew.

## Why the inputs are fixtures, and not generated

The rule above replaced three mechanisms that this repository had built and then
removed on 2026-10-07: tests that generated their inputs, random mutation of
fixtures, and an exploration command that put each of a fixed set of strings at
each place collected from the corpus. The record of that day is the reason the
rule is written as it is.

- Count is not assurance. The exploration ran about 130,000 inputs against
  mermaid.js in more than an hour of machine time and found four implementation
  bugs. Its places were (token kind before, token kind after, position in line)
  collected from the corpus: 1,210 kinds for flowchart, which multiplied some
  thirty lexical rules by the number of contexts each appears in. The two
  findings of its first run lay next to a separator, where the rule's own
  example would have been the host.
- Reading the sentences finds what a product cannot. In the same afternoon,
  listing the cases of each defining sentence and checking that each had a
  fixture found: in the specification about 440 places where a case had no
  fixture or no citation, 185 new fixtures and an unreachable rule copied from
  mermaid's lexer; in the documents of `dbFromTree` 306 missing fixtures, at
  least 23 wrong sentences and at least eight holes in the tree check; in the
  formatting rules 386 missing fixtures, four printer bugs and about fifteen
  sentences that did not describe the printer; in the rule documents 95 missing
  inputs, one suggestion that mixed line terminators, three suggestions that
  changed the reading, one that produced a rejected text, and three wrong
  sentences; in the parser's documents of tokens, positions, and error positions
  about 410 missing citations and 19 missing fixtures. A product of places and
  strings reads no sentence, so it cannot see a missing citation, a wrong
  definition, a suggestion that changes the Db, or a rule that no input reaches.
- The mechanism stood in for a habit. Generating inputs let a change be reported
  as done without anyone listing the cases of the sentence that defined it. The
  rule therefore names the habit, not a tool: write the sentence, list its
  cases, give each a fixture, cite them, and let the review read the sentence
  again.
