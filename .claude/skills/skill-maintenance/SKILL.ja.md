# スキルを作業ごとに分けて保つ（skill-maintenance）

`.claude/skills/<name>/` のスキルは、
その `SKILL.md` の `name` と `description` で選ばれ、
使うたびに `SKILL.md` の全体が読み込まれる。
この SKILL は、それが成り立つようにスキルをどう分け、
その分け方をどう変えるかを述べる。
すべての Markdown 文書に当たるもの（英語と日本語の対、折り返し、
検査）は SKILL `conventions` にある。

## 方針と基準

- 基準: ある作業をするセッションが、その作業の規則を読み込み、
  ほかにはほとんど読み込まず、当たる規則をどれも取りこぼさない。
  以下の規則は、それぞれこの基準を当てはめたもので、どの規則も扱わない場合は、
  この基準を当てはめて決める。
- 規則は 1 か所に書く。
  複数のスキルが必要とする規則は、
  関係するすべてのセッションが読み込む 1 つのスキル（パッケージの入口のスキルか
  `conventions`）に置き、ほかのスキルはそこへ案内する。
- 別のファイルへの案内は、セッションがそれをたどるという約束であり、
  それを強制する仕組みはない。
  そのため、案内でセッションを送る先は、作業の手順か記録だけにし、基準と、
  見落としてはいけない規則は、
  セッションが読み込むファイルに残す: その作業のスキルか、
  その作業のスキルが挙げ、
  description がセッションに読み込むよう案内する入口のスキルである。
- 分けるための作業（見出しと番号の変更、参照の書き換え）は、
  基準を満たさない分け方を保つ理由にならない。

## 1. 何をどこに置くか

- パッケージの入口のスキル（`spec`、`tests`、
  `parser`、...）: AGENTS.md
  がそのパッケージの方針と基準の置き場所として挙げる「方針と基準」の節、
  見落としてはいけない規則、そのパッケージのどの作業も従う手順。
  複数の作業が使う方法は、
  そうした手順であり（[`spec`](../spec/SKILL.ja.md) の Reading mermaid.js から
  Proposing a known divergence までの節）、
  その節の題が 1 つの作業の名前であっても同じである（`parser` では、
  [4 節 Adding a diagram type](../parser/SKILL.ja.md#4-図種を足すとき)
  の小節のうち、ほかの節が案内するか、ほかの節がその規則に従うもの）。
- `<package>-<work>` という名前の 1 つの作業のスキル（`tests-diagram-type`、
  `spec-diagram-type`、
  `tests-mermaid-update`）: そのパッケージのほかの作業とは別のときに、
  別の入力から、別の結果へ進む作業の手順。
  - その `description` は、何をするかといつ使うかを具体的に述べ、
    入口のスキルがその作業の規則を持つときは、
    末尾を "together with the <entry> skill" にする。
  - 本文は、その手順に当たる入口のスキルの節を挙げ、
    それらを先に読むように述べて始める。
  - 入口のスキルの `description` は、そのパッケージのすべての作業を、
    それぞれのスキルがある作業も含めて用途の中に挙げ、
    そうした作業にはそれぞれのスキルがあることを述べ、
    そうした作業をするセッションが入口のスキルも読み込むようにする。
  - 手順が入口のスキルの節を通るところでは、手順を順に挙げ、それぞれの節を題と、
    そのアンカーへのリンクで示す。
- 作業が必要なときにだけ読む文書は、
  `<skill>/references/<name>.md` に置く: 過去の判断の記録、
  1 つの項目を引くために検索する一覧、
  手順が動かすスクリプトのコードである（`rule-ideas/references/`、
  `prettier-plugin/references/`）。
  `SKILL.md` は、その文書を使う手順でそれぞれに直接リンクし、
  何で検索するかを述べる。
  `references/` のファイルだけが別のファイルへの道になることはない。
  `references/` のファイルが 100 行を超えるときは、
  内容をその順に挙げる目次で始める。
- 過去の判断の記録: 規則ごとの判断と、そのために確かめたこと。
  記録は、全体を読むのでなく検索する。
  - 記録が属するスキルの節は、何を検索するかを述べる: 規則の名前、
    注が規則のまとまりを扱うところではその `<diagram>-<name>` の形、図種の項目、
    図種の注の初めの段落。
  - 記録は、すべての規則の名前を省かずに書き、
    名前で検索すると見つかるようにする。
  - 新しい場合も決める文（1 つの規則についてでなく、
    規則の種類についての規則）は記録ではなく、記録の中に書かれたものであっても、
    スキルに置く。
- 作業が 1 つの項目を引くために、
  検索する一覧（整形ツールのソースのファイルごとのテストのファイル、
  `prettier-plugin/references/tests-by-changed-file.md` など）。
  記録と同じく、新しい場合を決める規則は持たない。
- AGENTS.md は、`packages/eslint-plugin` の項目が `rule-ideas`、
  `eslint-plugin`、`eslint-plugin-rules` を挙げるように、
  パッケージごとの項目で、その作業のすべてのスキルを挙げる。

スキルの公式文書は、この形を定めている。
[Agent Skills の仕様](https://agentskills.io/specification) は、
スキルのフォルダーに `SKILL.md` 以外のどんなファイルも置けるとし、
エージェントが必要なときに読む文書には `references/` を、
`SKILL.md` は 500 行未満で本文を 5,000 トークン未満にすることと、
`SKILL.md` から 1 階層の深さの参照を勧める。
[Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
は、すべての参照ファイルに `SKILL.md` から直接リンクすることと、
Claude が最初の数行しか読まないことがあるため、
100 行を超える参照ファイルは目次で始めることを加える。
[Claude Code のスキルの文書](https://code.claude.com/docs/en/skills) は、
そうしたファイルは必要なときにだけ読み込まれると述べる。

## 2. 分けるときと分けないとき

決める前に、各部分の大きさ（`wc -c`）を測り、
どの作業がその部分を使うかを調べる。
作業がある部分を使うのは、その手順がその部分へ案内するときと、
その手順ですることに当たる規則を、
その部分が持つときである（変更された規則を実装する手順は、節を挙げていなくても、
字句解析器と文法を書く規則に従う）。
判断とともに大きさと使う作業を示し、その判断を確かめられるようにする。
公式文書が勧める 500 行か 5,000 トークンを超える `SKILL.md` の本文も、
このように測る。
トークン数は、`wc -c` が数える本文のバイト数を 4 で割って見積もるので、
20,000 バイトを超える本文は勧めを超える。
その大きさを超えても残すのは、基準と、見落としてはいけない規則と、
そのスキルのすべての作業が使う手順であり、判断には、残す部分ごとに、
その大きさと、それを使う作業と、そのどれに当たるかを示す。

次のときは分ける。

- 1 つの作業だけが使う部分を、そのスキルのほかの作業が使わずに読み込んでいて、
  それらが読み込むもののうち、小さな割合では済まないとき。
  または、
- 過去の判断の記録をスキルの本文に持つとき: 記録はそのスキルの `references/`
  に移す。
  または、
- ほかのスキルのセッションが、ある部分だけを読むとき（`rule-ideas` が動かし、
  `eslint-plugin` と `eslint-plugin-rules` も動かすスクリプト）:
  その部分だけを読むよう、`references/` に移す。

次のときは分けない。

- 分けても、ほかの作業が読み込むものをほとんど減らせないとき。
  ほかの作業もその部分の大半を使うからである（`parser` では、
  [4 節 Adding a diagram type](../parser/SKILL.ja.md#4-図種を足すとき) が、
  変更された規則を実装するときにも従う字句解析器と文法を書く規則と、
  5 節から 7 節が番号で使う手順を持ち、入力、組み込み、
  その図種のパーサーの入口、文書だけが新しい図種だけのものである）。
  または、
- 分け出す別の作業がないとき: そのスキルは 1 つの作業の手順（`eslint-plugin`、
  `review`、`parser-performance-review`）か、
  すべての作業が共有する規則（`conventions`）である。

ある部分を 1 つの作業のスキルに移すとき、その中でほかの作業も必要とする文は、
入口のスキルの、
それらの作業がたどり着く節に残す（新しい既知の差異の文書をどう書くかは、
`spec` の
[既知の差異を提案する節](../spec/SKILL.ja.md#8-既知の差異を提案するとき)
にあり、欠落を直す作業は、
[規則を確かめる節](../spec/SKILL.ja.md#6-規則を確かめる) の項目 4
を通ってその節にたどり着く）。

2 つの作業が共有する手順（一方の作業中に一覧へ足し、
他方の作業中にその一覧から外すものなど）は、
両方の作業のスキルからたどり着けるようにする: その手順を持たないスキルは、
自分の手順の中で、
共有する手順を行う所でそこへ案内する（記録した木のない図種の一覧には、
`tests-diagram-type` の手順の中で足し、
[その手順](../tests-diagram-type/SKILL.ja.md#2-正規化関数)
が足し方と外し方を述べ、木が記録されると、
そこでその手順へ案内する [`tests-tree-checks`](../tests-tree-checks/SKILL.ja.md)
の手順 8 の中で外す）。
ほかの作業も読む節から手順を移すときは、その手順があった所に、
移した先への案内を置く。

## 3. テキストを変えずに移す

1. 移す前に計画する: 英語と日本語の各ファイルの行の範囲と、それぞれの移動先、
   範囲内で変える文（参照先が移る参照、見出し）のそれぞれと、
   その元のテキストと新しいテキスト、新しく書くテキストの全文である。
   行番号を使う前に、すべての範囲の境界の行をファイルで読む。
2. テキストを変えずに移す。
   変えるのは計画した文だけで、
   Prettier と `pnpm run lint:md --fix` による折り返しは変更としない。
   場違いに見える文、重複、古くなった文は、報告し、移動の中では直さない。
3. それぞれの範囲が、計画した変更を当てたうえで、
   新しい場所にちょうど 1 回あることを機械的に確かめる:
   英語は空白の連なりをそれぞれ 1 つの空白として読み、
   日本語はすべての空白を除いて比べる。
   どの範囲にも含まれないテキストを読む: それは計画した新しいテキストである。
4. 計画の表を使わずに、移動をもう一度確かめる: 元のファイルのすべての文を、
   新しいファイルと語ごとに比べ、順序を保ち、
   どの文も 2 か所に置かれていないことを確かめる。
   節の番号を変えたときは、比較では節の番号を 1 つの仮の文字列に置き換え、
   変更した参照のそれぞれを、元の番号と新しい場所の表と照らして確かめる。
   節の間を移った文を、元と新しい場所とともにこの比較に示し、
   失われた文と数えられないようにする。
5. 英語のファイルごとに、その `.ja.md` と照らして確かめる: 同じ `name` と、
   同じことを言う `description`（英語でも日本語でもよい）、
   同じ階層と番号で同じことを言う見出し、
   同じ数のコードブロック（字下げによるものも）、
   英語が言うことを言う日本語である。
6. `references/` のファイルごとに、そのスキルの案内が述べるとおりに、
   単独で挙げた規則と、まとまりについての注が扱う規則を検索し、
   両方が見つかることを確かめる。
7. 変えたスキルを、
   そのスキルを使う作業ごとのセッションとして読む: `description` と冒頭から、
   そのセッションは必要なスキルを読み込むか、
   読み込むものとそこにある案内によって、
   変更前にその作業に当たったすべての規則にたどり着くか、
   ほかにはほとんど読み込まないか（読み込むものの大きさを 2 節のとおり測る）。
   たどり着かなくなった規則は、その移動についての指摘事項である。
8. スキル `conventions` が挙げる文書の検査と、
   移動で壊れたリンクかアンカーを報告する `pnpm run lint:md` を走らせる。

## 4. 参照先を失う参照

移動や節の改名や番号の変更によって、参照が何も指さなくなったり、
別のものを指したりしても、どの検査も失敗しないことがある。
変更前に、変えるテキストと、その周りのテキストへの参照をすべて探す。

- 変える部分の近くだけでなく、各ファイルの全体で、番号による参照（`section 7`、
  `3.5`、`§5.3.8`、`item 3 of 3.3`、`7 節`、`3.4〜3.5`）、題による参照、
  相対的な参照（`above`、`below`、`here`、`this section`、`this document`、
  `the table above`、`上の`、`下の`、`この節`、`ここ`）を探す。
  残るテキストの相対的な参照が移すテキストを指すことも、
  移すテキストの相対的な参照が残るテキストを指し返すこともある。
- `node_modules` を除くリポジトリ全体で、
  スキルとその節への参照を探す: ほかのスキル、AGENTS.md、パッケージの文書、
  コードのコメント（`the tests skill`、`the spec SKILL`、`tests の SKILL`、
  `skills/<name>/SKILL.md`、アンカー付きのリンク）である。
- スキルだけを挙げる参照（"written with the steps of the tests skill"）は、
  分けた後も参照先があるが、
  意図した手順にもうたどり着かないかもしれない: 何を指すかを読み、
  その手順を持つスキルを挙げる。
- あるスキルから別のスキルの 1 つの節への参照は、
  その節のアンカーを持つリンクにし、
  節の改名や番号の変更を `pnpm run lint:md` が報告するようにする。
  いくつかの節をまとめて指す参照は、スキルへのリンクにして、節を挙げる。
- 変更後に、見つけた参照をそれぞれ読む: 変更前と同じテキストを指している。

## 5. どの検査も確かめないもの

次のことはリポジトリのどの検査も確かめず、
3 節の手順 4 から 7 と 4 節が確かめる: 移したテキストが元と同じことを言うこと、
文章で書かれた参照が意図したものに今もたどり着くこと、
記録のファイルへの案内で探すものが見つかること、各作業が、
当たるすべての規則に今もたどり着くこと、
`references/` の各ファイルにその `SKILL.md` からリンクしていること、
`.ja.md` のフロントマターが英語のファイルのものと同じことを言うこと。
