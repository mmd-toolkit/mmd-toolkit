# 規則のアイディアの探し方と採否の決め方（rule-ideas）

`@mmd-toolkit/eslint-plugin` （Mermaid の図のテキストのための ESLint
の言語プラグイン）について、規則の候補を探し、持つかどうか、名前、範囲、
`recommended` に入れるかを決める手順。
採否の基準は 2 節の「方針と基準」にある。

## 1. この手順の範囲と進め方

- 決めた結果は、6 節の形で示す。
  この手順は、2 節、7 節、8 節の記録のほか、リポジトリのファイルを書かない。
  その記録は、
  [references/adoption-decisions.ja.md](references/adoption-decisions.ja.md)、
  [references/recommended-decisions.ja.md](references/recommended-decisions.ja.md)、
  [references/suggestion-decisions.ja.md](references/suggestion-decisions.ja.md)
  である。
  作業用のスクリプトとその結果は、リポジトリの外の作業用ディレクトリに置く。
- 決めた結果は、次の手順でリポジトリに残す。
  - 規則の文書（`packages/eslint-plugin/docs/rules/`）は eslint-plugin の
    SKILL、
    規則（`packages/eslint-plugin/src/rules/`）は eslint-plugin-rules の SKILL
    に従う。
    規則は、落とすときも含め、文書と一緒に 1 つの変更で足し、名前を変え、消す。
  - 根拠の fixture が足りなければ、最小の入力と、それが答える主張を添えて、
    tests パッケージに頼む（`packages/tests/docs/maintaining-fixtures.md`）。
    fixture は、
    規則の文書の例と規則のテストに使う（eslint-plugin の SKILL の
    [4 節](../eslint-plugin/SKILL.ja.md#4-書く前と書いた後に確かめること)の手順
    4）。
- 主張ごとに、【実行】（動かして確かめた）、【読解】（読んで確かめた）、
  未確認を示す。
  誤りと分かったら、その言葉で撤回する。
- 根拠にする前に、いまの仕様を読む。
- 作業ツリーをほかの作業と共有しているとき:
  - ほかの作業者が編集中のファイルに触らない。
    片方の変更が消え、編集が止まるのを待っても防げない。
  - 削除や置き換えの前に、対象の中身を読む。
  - git のステージを変えない。
    git mv、git rm も使わない。

## 2. 採否の基準と、その当て方

### 方針と基準

- 規則が報告するのは、書き手の誤りのうち、mermaid.js が黙って受理し、
  意図と違うものとして読むものである。
  打ち間違い、閉じ忘れ、壊れた JSON、id の使い回しなど。
  規則ごとに、普通の書き方の例を pin した mermaid.js で動かし、
  その例を整形して確かめる。
- 規則が報告する場合ごとに、mermaid.js の出力は、何かを失う、置き換える、
  効かなくする、書いていないものを加える、のどれかであり、その場合は、どの値、
  どのテキストかを言う。
  前の `accTitle` が置き換わる、方向の行のテキストが捨てられる、
  閉じが形に効かない、どの文も書かない状態ができる、などである。
  mermaid.js の文書が定める値域や語の外の値（5 より大きい score、
  `excludes` の知らない語）は、その文書を根拠に効かない。
  mermaid.js が文法どおりに読み、何も失われない書き方は、
  書き手が別の構文のつもりだったと推定できても、規則にしない。
  ノードの行の `Write ::icon(fa fa-book)` は、
  ラベル `fa fa-book` を持つノード `Write ::icon` である。
- 次の種類の規則は持たない。
  - 文体の規則。
    mermaid.js が書かれたとおりに読んでいて、
    後の編集で壊れることだけを防ぐもの。
    例外が 1 つある。
    mermaid.js の文書が示さない形に頼る書き方は避ける。
    そのため、flowchart と agentflow の `linkStyle` と `classDef` で、
    `:` の前に空白を置いて書いた `stroke` は、
    いま何も失われないところでも報告する（7 節の注、
    [references/recommended-decisions.ja.md](references/recommended-decisions.ja.md)）。
    `style` はリンクにスタイルを付けないので、その `stroke` は報告しない。
  - 意図して分かりにくく書いたテキストのための規則。
  - mermaid.js の不具合のための規則。
    書き手が正しく意味の通る書き方をしているのに、
    mermaid.js が誤って読むもの（`subgraph Front end`、ラベルの中の CSS）。
    書き手に直すものはない。
    規則は言語の定義でなく実装に頼るので、不具合が直ると正しい文を誤りと言う。
    直す場所は mermaid.js である。
    場合がそうした不具合であるのは、
    テキストが mermaid.js の文書の示すとおりに書かれ、
    ほかのどの書き方でも失われるものを避けられないときだけである（`links`
    の中のフラグメントのある URL）。
    何も失わない形を文書が示しているときは、
    誤りのままである（`note left of A:hi`。文書は `:` の後に空白を置く）。
    持つ規則は、木が誤りと見分けられるところではそうした不具合を条件から除き、
    見分けられないところでは、
    7 節が言うとおり誤りと一緒に報告する（ラベルの中の `direction LR`
    のテキスト）。
  - 条件が、書き手が意図した書き方にも当てはまる規則。
    `A[Issue #123; fixed]` は、エンティティ `#9829;` と同じ形をしている。
  - このプロジェクトのフォーマッターが見える形にするもののための規則。
    `A---orders` は `A ---o rders` と印字される。
    保守するものが 2 つになるだけである。
  - 当面は、構文を知らないことから起きる誤りのための規則。
    その書き方が別の意味になることが、仕様の文法や本文に書いてあるもの。
    括弧のない `A"Start"`、スタイルの間の `;` など。
- 規則を共通の規則にするのは、
  木のうち全図種が共有する部分についての 1 つの定義で全図種を扱え、
  どの図種でも同じに振る舞うときだけである。
  そうでなければ図種の規則で、
  名前は `<図種>-` で始まる（文書は `docs/rules/<図種>-<名前>.md`）。

判断の前に毎回読む。

### 判断の例（【実行】）

これまでの判断（残した規則と落とした候補、それぞれの mermaid の結果）は、
[references/adoption-decisions.ja.md](references/adoption-decisions.ja.md)
にある。
候補を出す前に、そのファイルを検索して、その候補についての過去の判断を探す。
多くの行は図種を言葉で書いて始まる（`state の図で、`、`journey の図で、`、
`すべての図種で、`）。
ほかの行は図種を書かないので、入力のキーワードと規則の名前でも検索する。

### 迷ったときの問い

1. その入力を書くのは、普通に図を書いている人か。
   仕様の珍しい例をなぞっていないか。
2. mermaid は、いま、書かれたものと違う結果を出すか。
   後の編集で壊れるだけなら文体の規則。
3. 規則の条件は、文書化された正しい書き方や、
   意図して書いた書き方にも当たらないか。
   当たるなら持たない。
   報告しない例として、意図した書き方を必ず 1 つ mermaid で動かす。
4. その書き方が別の意味になると、仕様の文法や本文に書いてあるか。
   書いてあり、構文を知っていれば書かないなら、当面は持たない。
   構文を知っている人がうっかり起こすもの（閉じ忘れ、打ち間違い、
   id の使い回し）は残す。
5. 報告する例を整形すると（4 節）、mermaid の読み方が見える形になるか。
   なるなら持たない。
   字下げのずれや空白の付き方の違いのような弱い手がかりは、数えない。
6. 書き手は正しく意味の通る書き方をしているのに、
   mermaid がそれを誤って読んでいないか。
   不具合のような挙動なら、mermaid のメンテナーが不具合と認めたか、
   文書に書かれているか、直される見込みがあるかによらず、規則にしない。
   それらの事実は、判定とともに記録する。
   (a) mermaid の文書の、その構文の節と、ページの冒頭の警告を読む。
   (b) issue と PR を、題（`in:title`）と本文の両方で、語を別々にして探し、
   探した語を記録する。
   (c) 誤った結果が、Db だけでなく、描かれた図で利用者に見えるかを言う。
   mermaid への報告はこの手順の外で、根拠が要る。
7. 決めきれないとき（空の `%%` 行、行末の空白）は、
   両方の理由を付けて決定を求める。

## 3. 材料の探し方

- 仕様: `packages/spec/docs/common.md` と
  `packages/spec/docs/diagrams/<図種>.md`。
  規則の帰結として書かれた、受理されるが意外な読み方を拾う。
- fixture: `packages/tests/fixtures/<図種>/` の `input.mmd`、`expected.json`、
  `ast.json`。
  とくに名前が `lex-`、`gram-`、`db-` で始まるもの。
- フォーマッターの制限: `packages/prettier-plugin-mmd/docs/<図種>.md` と
  `docs/compatibility.md`。
  空白 1 つや `;` 1 つで意味が変わる箇所が並んでいる。
- 既存の規則: `packages/eslint-plugin/docs/rules/`。
  同じものを出さない。
- 自分で探す: 書き手の側の誤り（閉じ忘れ、打ち間違い、id の使い回し、
  壊れた設定の JSON、コメントアウトの残り）から始めて、mermaid を動かす。
  仕様の珍しい例から始めると、意図して分かりにくい入力ばかりになりやすい。
  普通の書き方を mermaid が誤って読む例（subgraph の名前の語 `end`
  が改行を取り込む）は、規則でなく mermaid の不具合の候補として示す。

## 4. mermaid と parse() で確かめる手順

mermaid.js と `parse()` を入力の一覧に流すスクリプト（`probe.mts`）と、
整形するスクリプト（`format.mts`）は、置き方、入力の書き方、実行の仕方とともに、
[references/probe-scripts.ja.md](references/probe-scripts.ja.md) にある。

- 1 つの候補につき、次の 3 つを同時に流す。
  - 報告する例（普通の書き方）
  - 報告しない例（直した書き方）
  - 意図した書き方（2 節の問い 3。例: `#9829;`、`R&D`）
- 条件や提案の各主張は、その主張が分ける場合ごとの入力で確かめる。
  その場所で出会うほかの決まり（ディレクティブ、無視される `;`、コメント行、
  空行、行区切り、空の説明ブロック）ごとの入力でも確かめる。
  conventions の SKILL
  の「[テストの実行](../conventions/SKILL.ja.md#テストの実行)」のとおりで、
  入力はこれらの場合から選び、生成しない。
- 規則の場合の表を示す前に、その表を下の場合の種類に当て、
  文書の文が触れる種類ごとに行を加え、文に書く前に mermaid.js で走らせる。
  - 後の行から値を取る文で、間に空行、コメント行、
    ディレクティブがある形（`%% c` の後や `%%{init: {}}%%` の後の行を取る、
    2 つ目の `accTitle:`）
  - 大文字小文字を問わず読むと文が言う語を、
    ほかの大文字小文字で書いた形（`TITLE`、`Until`）と、
    後の空白なしで書いた形（`untilb1`）
  - 前の文と比べる規則では、mermaid.js が何を残し何を捨てるかから、
    比べる相手（最初のもの、同じ種類の最初のもの、直前のもの）を先に決め、
    規則が分ける種類と形を混ぜた 3 つを書いて、
    最初の文と 3 つ目の正しい相手が違うようにし（同じ名前の requirement、
    element、requirement で、3 つ目は 2 つ目と比べる。直前と比べる規則では、
    間に空のブロックのような数えない値を挟んだ 3 つ目）、
    メッセージがその相手を名指すかを確かめる。
    同じ形の 3 つ目は報告 2 である。
  - そうした規則で、置き換える値と同じ値を設定する文。
    mermaid.js が同じ値として持つ別の書き方（両端の空白、文字列と同じテキスト、
    ほかの大文字小文字）も含む。
    何も失わないので、報告しない。
  - 規則が数えない値の種類のそれぞれ（空のブロック、コメント行だけのブロック、
    ディレクティブだけのブロック）
  - 規則が隣の規則と出会う入力（ユーザージャーニーの `A: 5:: x`、
    空の人と捨てられるテキスト）
  - 空の項目の連なりと、区切りだけの一覧（`a,,b`、`,`）
  - それぞれの形の対になる形（`after` に対する `until`、開始に対する終わり）
  - mermaid.js が読む値を終える文字（`.`、タブ、ASCII でない文字）と、
    CRLF で書いた行末
  - mermaid.js がまったく読まず、
    どの規則も報告しないデータ（gantt の 4 つの項目のデータ）
- 結果が変わるかは、受理と拒否と、
  `runMermaid` がすべての図種で返す Db の要約で判断する（正規化関数は
  `packages/tests/src/normalizers/index.ts`）。
- 木での現れ方は、`parse()` の結果に条件を当てて確かめる。
  条件は、ノードの欄、トークンの種類と値、`Root.comments`、
  `Root.directives` で書き、テキストを字句解析し直さない。
  葉のノードの値の中を探す必要があるときと、
  木とトークンから見つけられないときは、そう書く。

## 5. 共通の規則か、図種の規則か

条件は、2 節の「方針と基準」の最後の項目である。
共通の構文（`common.md` の規則）が原因でも、
図種の字句解析器が吸収したり拒否したりするなら、共通にしない。

確かめ方:

1. 図種とその先頭の語を、手で書いた一覧でなく、
   `packages/spec/docs/detection.md` の表から取る。
2. 図種ごとに、その語で始まる最小の図を作り、mermaid が受理することを確かめる。
   固定版の mermaid.js は次の図を受理する【実行】。
   括弧内は、mermaid が返す図種の id。
   ほかは要るときに作る。
   - `sequenceDiagram`、改行、`A->>B: hi`（sequence）
   - `classDiagram`、改行、`class A`（classDiagram）
   - `stateDiagram-v2`、改行、`[*] --> A`（stateDiagram）
   - `erDiagram`、改行、`A ||--o{ B : has`（er）
   - `gantt`、改行、`title T`、改行、`section S`、改行、
     `Task :a1, 2024-01-01, 1d`（gantt）
   - `pie`、改行、`"a" : 1`（pie）
   - `journey`、改行、`title T`、改行、`section S`、改行、
     `Task: 5: Me`（journey）
   - `gitGraph`、改行、`commit`（gitGraph）
   - `mindmap`、改行、`root`、改行、`  A`（mindmap）
   - `timeline`、改行、`title T`、改行、`2020 : a`（timeline）
   - `quadrantChart`、改行、`x-axis Low --> High`（quadrantChart）
   - `requirementDiagram`、改行、`requirement r {`、改行、`id: 1`、改行、
     `}`（requirement）
   - `block`、改行、`A`（block）
   - `xychart`、改行、`x-axis [a, b]`、改行、`bar [1, 2]`（xychart）
   - `sankey`、改行、`A,B,1`（sankey）
   - `packet`、改行、`0-15: "A"`（packet）
   - `kanban`、改行、`todo`、改行、`  a`（kanban）
   - `architecture-beta`、改行、`service a(server)[A]`（architecture）
   - `C4Context`、改行、`Person(a, "A")`（c4）
   - `radar-beta`、改行、`axis a, b, c`、改行、`curve c1{1,2,3}`（radar）
   - `treemap-beta`、改行、`"A"`、改行、`  "B": 1`（treemap）
   - `info`（info）
3. その構文を各図に入れて mermaid に通す。
   拒否する図種では規則は要らない。
4. 受理する図種では、pin した mermaid のビルドでその字句規則を読み、
   結果が変わるかを確かめる。
   - 場所は
     `node_modules/.pnpm/mermaid@<版>/node_modules/mermaid/dist/chunks/mermaid.core/`。
     ファイル名は次のどれかの形である。
     - `<名前>Diagram-*.mjs`（sequenceDiagram、pieDiagram など）
     - `<名前>-definition-*.mjs`（timeline、mindmap、kanban）
     - 名前のない `diagram-*.mjs`（packet、radar、treemap など）。
       図種の id で `grep -l` して探す。
   - jison の図の字句規則（`/^(?:...)/` の形の正規表現）は、
     `grep -o` で抜き出す。
   - Langium の図にはその規則がない（pie、gitgraph、info、architecture。
     【実行】）。
     Db が変わるかは未確認として扱う。
5. 例: `%%` だけの行。
   - flowchart-v2 だけが頂点 `%%` を作る【実行】。
   - er と sankey は拒否する【実行】。
   - sequence、classDiagram、stateDiagram、gantt、journey、timeline、mindmap、
     kanban、c4、quadrantChart、xychart には、
     `%%` で始まる行をコメントとして読む字句規則がある。
     grep で抜き出して確かめた【実行】。
   - そのため、この規則は flowchart の規則である。

## 6. 決定として示すもの

決めた規則ごとに、次を示す。

- 規則の名前（`<図種>-<名前>`、共通なら `<名前>`。
  id は `@mmd-toolkit/` の後に名前を付けたもの）と、共通か図種か。
- 何を報告するか（1 文）。
- 理由: mermaid がどう読むか、なぜ普通の書き方で起き、
  書かれたものと違う結果になるか。
- 報告する例、報告しない例、意図した書き方の例。
  どれも受理される普通の書き方で、mermaid の結果を付ける【実行】。
  振る舞いを確かめるために足した前置き（前の説明など）は、例でなく、
  理由と fixture に書く。
- 木での現れ方: どのノード、欄、トークンで見つけるか。
  `parse()` で確かめた結果【実行】。
- 根拠の fixture: 既にあれば名前。
  なければ、足すべき最小の入力と対照例。
- `recommended` の設定が有効にするかと、その理由。
  7 節で決める。
- 提案と、提案を付けないならその理由。
  8 節で決める。
- オプションと、後で足すことを考えるオプションとそれを足す条件。
  下の表に記録する。
  規則の文書は、規則が持つオプションだけを書く。

落とすと決めたものも示す。
名前と、2 節の「方針と基準」のどの項目で落としたかを書く。

規則の文書を書く途中で、新しい候補、範囲や名前の変更の必要、
木から見つけられないことが分かったら、同じ基準で決め直し、
その結果を同じ形で示す。

オプションの判定:

| 規則                                                                      | オプション | 後で足すことを考えるもの                                                                                   |
| ------------------------------------------------------------------------- | ---------- | ---------------------------------------------------------------------------------------------------------- |
| flowchart-no-empty-description-block、sequence-no-empty-description-block | なし       | 規則が報告しない、コメントだけを持つブロックも報告すること。この規則を使う人から要望があったときにだけ足す |
| ほかのすべての規則                                                        | なし       | なし                                                                                                       |

## 7. `recommended` に入れるか

`recommended` は、報告がほぼいつも直すべき誤りである規則の集まりである。
どの規則もそうした誤りを報告する（2 節）ので、持つ規則は、
次の基準のどれかを満たさない場合のほかは、入れる。

1. **報告がいつも事実である。**
   規則が報告するどの場所でも、mermaid.js は、
   テキストを書き手のつもりと違う読み方をする（捨てる、別のものに読む、
   拒否する、前の値を置き換える）。
2. **意図した書き方を報告しない。**
   書き手がわざとそう書く形が、条件に当たらない。
   持つ規則はふつう満たし、満たすかに疑いが残る規則は入れない。
3. **報告が、変わる見込みのある mermaid.js の振る舞いに乗っていない。**
   その振る舞いを直す PR が開いておらず、
   mermaid.js のメンテナーが直すと言っていない。
   mermaid.js が変わると、報告が事実でなくなるからである。
4. **直し方がはっきりしている。**
   報告を受けた書き手が、何に書き換えればよいかが分かる。

同じノードにあるために誤りと一緒に報告される mermaid.js の不具合は、
入れるのを妨げない（flowchart-no-ignored-text
が方向の行の上のテキストと一緒に報告する、
ラベルの中の `direction LR` のテキスト）。
mermaid.js はそのテキストも捨て（基準 1）、
書き手はテキストを書き換えて避けられる（基準 4）。

規則ごとに、その文書に照らして、場合ごとに判定する。

1. 基準 1: 文書が分ける場合ごとに調べる。
   mermaid.js は書いたとおりに読むが報告する、と文書が書く場合も調べる。
2. 基準 2: 場合ごとに 2 節の問いで調べる。
   報告が、出力が何を失う、置き換える、効かなくする、加えるかを、
   書き手のつもりの推定なしに言い、mermaid.js の文書が示す書き方を報告しないか、
   である。
   後で埋めるために残した空のブロックのように、
   書き手がその形をわざと書きうるところでは、そこで報告が何を言うかを注に書く。
3. 基準 3: 規則ごとに mermaid.js の issue と PR を検索し、
   検索語と見つかったものを記録する。
4. 基準 4: 何に書き換えればよいかを文書が書いているかを調べる。

規則ごとの判定と、基準ごとに調べたことは、
[references/recommended-decisions.ja.md](references/recommended-decisions.ja.md)
にある。
規則の判定は、そのファイルを規則の名前で検索して探す。
その図種の注の初めの段落（`XY チャートの規則。`）、
規則を `<diagram>-<名前>` の形で図種の一覧とともに挙げる、規則のまとまりの注、
見つけた注が指す注（`上のタイトルの規則の注`）も読む。

## 8. 提案

持つ規則に、提案か自動修正を付けるかと、その中身を決める。
提案は、エディタで利用者が選んだときだけ適用される書き換えである。
書き換えの候補は、次の 5 つの基準を満たすときだけ提案にする。

提案を付けないことは、守りを要する提案を付けるより良い。
候補は、それが正しい条件を仕様の文 1〜2 文で書けるときだけ出す。
結果の parse、既知の差異ごとの判定、
図種ごとの例外がないと成り立たない候補は出さず、候補を守るために条件を足さない。
1 つの規則の中でも同じで、そうした文が言える場合（行を独り占めする文だけを消す、
コメントのない範囲だけを詰める）にだけ書き換えを出し、ほかの場合は出さない。

1. **候補が、報告した書き方から決まる少数である（1〜3）。**
   書き換えが書くものは、木とそのトークンの位置と、ノードの値から決まる。
   新しい名前が要る書き換え（打ち間違えた id を別の id に、
   使い回した id を新しい id に変える）は候補にしない。
   どの名前のつもりかをテキストは示さないからである。
2. **どの候補も、書き手のつもりでありうる。**
   結果は、その誤りをした書き手が書こうとした形の 1 つである。
   書き手のつもりにかかわらず、規則を黙らせるだけの書き換えは候補にしない。
3. **条件を仕様の文から書き、規則がその場所をもう報告せず、
   書き換えが新しい誤りを書かない。**
   どの書き換えも、規則を走らせるときに結果を parse しない。
   1 行に約 0.04 ms かかるので、1,000 行の図に報告が 100 あると、
   lint のたびに約 9 秒かかる。
   ブロック、ディレクティブ、逆引用符、
   名前が取っていた行を文に戻す書き換え（ブロックを `{` の行の終わりで閉じる、
   treeview の名前を閉じる、ディレクティブを閉じる、逆引用符の名前を閉じる）と、
   `;` で行を分ける書き換えは出さない。
   それらの行が文に戻るか、mermaid.js がそれをどう読むかは、
   結果の全文を parse し、既知の差異について調べないと分からず、その差異は、
   仕様が述べない mermaid.js の字句解析の手順を写すことになるからである。
   空のまま閉じていないブロックを閉じる書き換えは候補にしない。
   空のブロックを書き、no-empty-description-block がそれを報告するからである。
   ほかの規則が結果を報告してよいのは、書き手のテキストがもう持っていた誤りを、
   書き換えが見えるようにするときだけである。
   前の説明の後の閉じていないブロックを閉じると、
   テキストが説明を 2 度設定していることが見え、
   no-duplicate-description がそれを報告する。
   規則のテストは、その提案がこのように見えるようにしうる規則を、
   それぞれが示す誤りとともに挙げ、結果にほかの規則の報告があれば失敗する。
   それは規則の文書でなく、
   この節と
   [references/suggestion-decisions.ja.md](references/suggestion-decisions.ja.md)
   が記録し、fixture が示す。
4. **結果を mermaid.js がどう読むかが分かっている。**
   この節と
   [references/suggestion-decisions.ja.md](references/suggestion-decisions.ja.md)
   の記録、fixture がその読み方を持ち、
   例を mermaid.js で走らせて確かめる（実行）。
   提案のメッセージは、
   読み方でなく書き換えだけを言う（``Remove this `accTitle` statement.``、
   ``Remove the earlier `accTitle` statement.``、`Remove the empty block.`、
   `Close the block at the end of the text.`）。
   読み方は結果が示し、それを言う節は、
   同じ値を設定する 3 つの文の 2 つ目では偽になる。
5. **結果が、見えない空白に頼らない。**
   行末の空白でだけ読み方が変わる書き換え（`%%`
   の後に空白を足す）は候補にしない。
   エディタが保存のときに行末の空白を消すと元に戻るからである。

書き換えを提案でなく自動修正（`meta.fixable`。
`eslint --fix` とエディタが保存のときに当てる）にするのは、
次の 2 つがともに成り立つときだけである。
1 つ目に、結果が書き手のつもりだと疑いなく言え、
mermaid.js がそれをつもりどおりに読む。
テキストが許す書き換えがこの 1 つで、
書き手が別のつもりで書いたかもしれないものを、消しも足しもしない。
2 つ目に、書き換えを決めるものが、書き換える範囲と自分の文の中にある。
`--fix` は、同じテキストで見つけたすべての規則の修正のうち、
範囲が重ならないものを 1 回の通しでまとめて当て、それから lint し直し、
それを 10 回まで繰り返す（ESLint の `lib/linter/source-code-fixer.js` と
`MAX_AUTOFIX_PASSES`）。
そのため、ほかの行を読む条件を持つ修正は、
同じ通しのほかの規則の修正で誤りになりうる。
修正を差し止めるだけの条件は、その条件が探す形をどの修正も作らないなら、
ほかの行を読んでよい。
修正は後の通しで当たる。
自動修正を出す報告は、同じ書き換えの提案を出さない。
自動修正の条件が成り立たない報告では、その書き換えを提案として出す。
どの書き換えを自動修正にするかは、
[references/suggestion-decisions.ja.md](references/suggestion-decisions.ja.md)
の「自動修正」に挙げる。

規則の文書の本文は、
提案に触れない（SKILL `eslint-plugin` の
[3 節](../eslint-plugin/SKILL.ja.md#3-文書の形)）。
提案や自動修正があることは生成する告知が言い、
それぞれのメッセージはその書き換えを言う。
書き換えごとに何を変えるか、どんな条件で出すか、結果を mermaid.js がどう読むか、
何を見えるようにしうるか、規則が提案を付けない理由、
それを説明する mermaid.js のソースへのパーマリンクは、
この節と
[references/suggestion-decisions.ja.md](references/suggestion-decisions.ja.md)
に記録する。
実装はこの記録に従い、規則のテストがそれを確かめる。
読み方は、各規則の invalid の fixture で確かめた（実行）。

### 書き換えの種類

どの書き換えも、ディレクティブを一緒に消さない。
消すか置き換える範囲の中にディレクティブがあるときは、書き換えを出さない。
ディレクティブの設定も一緒に消えるからである。
sankey の `a,b,1%%{init: {"theme":"dark"}}%%_000` を `a,b,1000` と書き換えると、
受理されるが（実行）、ディレクティブは消え、それとともにテーマも消える。
範囲の隣のディレクティブはそのまま残る（block-no-spaced-class-id が消す、
ディレクティブの後の空白）。
ディレクティブの中の書き換え（no-invalid-init-directive、
no-duplicate-init-key）は、その引数だけを変える。
fixture: 上の sankey の値（出さない）と、
ディレクティブのない同じ規則の値（出す）。

- 文を消す: 文を、その行と行終端と一緒に消す。
  文が行を独り占めするときに限る。
  最初の行で前に、最後の行で後に、空白のほかの文字もコメントもなく、ほかの文、
  `;`、コメントが行を分け合わないときである。
  flowchart の、
  テキストを次の行に書いた `accTitle:` のように複数の行にわたる文は、
  そのすべての行と一緒に消す。
  ほかの文、`;`、コメントと行を分け合う文は消さない。
  `A --> B; accTitle: x` と `accTitle: style:#b;` はその行を保つ。
  重複では、mermaid.js は残った最後の説明かタイトルを使う（実行）。
  subgraph の中の説明は、Db では subgraph のメンバーでもあるので、
  消すとメンバーも変わる（実行）。
  fixture: それだけの行の文（出す）。
  行で後にほかの文がある文、`;` の後の文、行で後にコメントがある文（出さない）。
  テキストが次の行にある `accTitle:`（出す。両方の行を消す）。
- 前の文を消す: その後規則がこの文を報告しないときだけ出す（`accTitle: A`、
  `accTitle: A`、`accTitle: B` で 2 つ目の `A` を消すと、
  `B` が最初のものを置き換えたままで、基準 3 に反する。実行）。
  部分では、前の部分について同じである。
- eventmodeling の行の文を消す: `accTitle:` や `accDescr:` の行の形は、
  ふつう行でほかの文の後に書く（`eventmodeling accTitle: First`、
  `tf 01 evt Bought accTitle: Second`）。
  そうした行の文は前の ASCII の空白かタブを取り、
  その文字は行末か最初の `%%`
  までなので（`packages/spec/docs/diagrams/eventmodeling.ja.md` の共通の形）、
  前の文はその空白の前で終わる。
  そこでは、行でその文の後に何もないとき、その文を、前の空白とタブと一緒に、
  行終端を除いて行末まで消す。
  後に `%%` があるときは出さない。
  規則の invalid の fixture と eventmodeling のコーパスにある、
  そうした文をそう消すと、どれもパーサーと mermaid.js が受理し、
  mermaid.js はタイトルと説明のほかを前と同じに読む（実行）。
  fixture: ヘッダーの後（出す）、frame の後（出す）、
  後にコメントがあるもの（出さない）。
- 文の一部を消す（gitgraph-no-duplicate-option、radar-no-duplicate-option、
  quadrant-no-duplicate-style、venn-no-duplicate-style、
  usecase-no-duplicate-metadata、treeview-no-duplicate-annotation、
  no-duplicate-init-key、journey-no-empty-person）: その部分を、
  隣の区切り 1 つと一緒に消す。
  区切りが単独で残らず、一覧がその形を保つようにするためである。
  部分を `,` で区切る一覧（radar のオプション、quadrant と venn のスタイル、
  usecase の metadata、JSON のオブジェクトのメンバー、journey の人）では、
  その部分の前の `,` を消し、最初の部分ではその後の `,` を消す。
  どちらも、部分の側の隣の空白と一緒に消す。
  部分を空白で区切る一覧（gitgraph のオプション、
  ノードの行の treeview の注釈）では、その部分の前の空白を消す。
  文のただ 1 つの部分は、部分としては消さない。
  代わりに、文の条件で文を消す（radar のオプション、venn のプロパティ、
  usecase の更新）。
  `systemBoundary` の usecase の見出しでは、代わりに metadata のブロックを消す。
  境界の metadata はなくてよいと `packages/spec/docs/ast/usecase.ja.md`
  が書くので、文法はそれを許す。
  それだけの行にある treeview の注釈は、文の条件で、行ごと消す。
  結果は、それぞれの一覧の文法が許す形なので、ほかの確かめは要らない。
  gitgraph には、
  [references/suggestion-decisions.ja.md](references/suggestion-decisions.ja.md)
  のその規則に書く条件がある。
  fixture: 一覧の最初、途中、最後の部分（どれも区切りと一緒に出す）。
  文のただ 1 つの部分（文を消すか、文が行を分け合うなら出さない）。
  ノードの行の treeview の注釈と、それだけの行の注釈。
- 行終端をまたいで消すか詰める: 行終端を持つ範囲を消すか 1
  行に詰める書き換え（区切りの前後や括弧の中の、行をまたぐ空白、
  行をまたぐ文の一部、つなぐ行の前の改行）は、範囲にコメントがなく、
  範囲の最初と最後の行のほかの行が空か空白だけのときだけ出す。
  そうでないと、端の行をつなげたとき、コメントが後の文字を取るか、
  間の行が値に入ることがある。
  fixture: block-no-invalid-direction の `A<["x"]>(right`、`%% c`、
  `down)`（出さない。パーサーも mermaid.js も受理する。実行）と、
  `A<["x"]>(right ,`、空の行、` down)`（出す）。
- 空のブロックを消す: 文の条件で消す。
  flowchart では、空のブロックを消しても Db は変わらない（実行）。
  ディレクティブを持つブロックは、上のディレクティブの規則により消さない（実行。
  消すと、subgraph が `inheritDir` で得た方向を失う）。
  ブロックが説明を空にする図種（architecture、cynefin、gitgraph、packet、pie、
  radar、railroad、treemap、treeview、usecase、wardley）と、
  自分の文字を説明にする図種（eventmodeling）では、
  mermaid.js はそれから最後に残った説明を使い（実行）、
  no-duplicate-description が後の文を報告することがある。
  eventmodeling では、行の文と同じく、ブロックは行でほかの文の後にあり、
  後にほかの文が続くこともある（`eventmodeling accDescr {} tf 01 evt Bought`）。
  行の始めのブロックは拒否される（実行）。
  ただし `---` のブロックの後では行を独り占めし、文の条件が当たる。
  そこでは、ブロックを行で前にある空白とタブと一緒に消し、後にあるものは残す。
  規則の invalid の fixture と eventmodeling のコーパスにあるものと、
  問いから書いた入力（ヘッダーの後、frame の後、後に frame、`accTitle:`、
  コメントがあるもの、テキストの終わり、
  行をまたぐブロック）のブロックをそう消すと、
  どれもパーサーと mermaid.js が受理し、
  mermaid.js は説明のほかを前と同じに読む（実行）。
  fixture: それだけの行の空のブロック（出す）と、eventmodeling のほかで、
  行で文の後にあるもの（出さない）。
- ブロックをテキストの終わりで閉じる: `}`
  のないブロックが受理される図種（agentflow、flowchart、sequence、state、
  xychart）で、最後の行の後に `}` の行を足す。
  ブロックが `{` の行より後の行にテキストを持つときに限る。
  この書き換えは行を戻さない。
  閉じていないディレクティブを持つブロックには出さない。
  そのディレクティブから後は、
  ディレクティブが mermaid.js の読み方を決めるからである（実行。`d`、
  `more %%{wrap`、`A --> B` を持つブロックをテキストの終わりで閉じると、
  説明 `d` と `more --> B` になる）。
  テキストの終わりで開いたままの、`Long` と `text` の行を持つブロックは、
  テキストの終わりで閉じると、その 2 行を説明に持つ（実行）。
  見えるようにしうるもの: ブロックの前で説明を設定したときの
  no-duplicate-description（`accDescr: d` の後の `accDescr { x` を閉じると `x`
  になる。実行）。
  後の `}` が閉じるブロックも報告し、提案は出さない。
  `accDescr { first` の後の `B --> C`、`A{y}`、`D` の行は、説明 `first`、
  `B --> C`、`A{y` と頂点 `D` だけになる。
  `A{y}` の `}` がブロックを閉じるからである（実行）。
  条件は、ブロックのテキストが、ブロックの `{` より後の行に `{` を持ち、
  閉じる `}` がその行に単独でないことで、ブロックを閉じる `}` は、
  その行の形かデータブロックのもの（行をまたぐものも含む。`B{` の後の `y}`。
  実行）である。
  `}` の前にその行で空白とディレクティブしかないとき、後に何があっても、
  `}` はその行に単独である（`};`、`} C`。実行）。
  `accDescr {`、`uses { here`、`}` は書き手の `}` で閉じる。
  `{` の行の `}`（`accDescr { a { b }` は `a { b` になる）と、
  行に単独の `}`（`accDescr { x {` の後の `}` は `x {` になる）は、
  書いたとおりにブロックを閉じ、報告しない（実行）。

### 規則

規則ごとの書き換えと、どの書き換えを自動修正にするかは、
[references/suggestion-decisions.ja.md](references/suggestion-decisions.ja.md)
にある。
規則のものは、そのファイルを規則の名前と、
規則のまとまりの項目が図種の一覧とともに使う `<diagram>-<名前>` の形で検索し、
その図種の項目（`- class:`）も読む。

報告が、別の値のためにもう一度書いた要素、ラベル、名前で、
ありうる直しが新しい id や名前である規則は、基準 1 により提案を付けない。
2 つのつもりだったとき、2 つの一方を消すのは規則を黙らせるだけだからである。
報告が、1 つの要素にもう一度書いた設定、スタイル、オプションである規則は、
2 つの削除を付ける。
