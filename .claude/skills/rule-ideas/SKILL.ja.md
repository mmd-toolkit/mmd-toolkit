# 規則のアイディアの探し方と採否の決め方（rule-ideas）

`@mmd-toolkit/eslint-plugin` （Mermaid の図のテキストのための ESLint
の言語プラグイン）について、規則の候補を探し、持つかどうか、名前、範囲、
`recommended` に入れるかを決める手順。
会話の履歴や記憶がなくても、この文書だけで同じ判断ができるように書く。
採否の基準そのものは 2 節の「方針と基準」にあり、この文書のほかの所には、
基準の当て方を書く。

## 1. この手順の範囲と進め方

- この手順が決めるのは、規則の採否、名前、範囲、
  `recommended` の設定がその規則を有効にするか。
  決めた結果は、6 節の形で示す。
- この手順そのものは、リポジトリのファイルを書かない。
  ただし、この文書の 7 節の、`recommended` の判定の記録は書く。
  作業用のスクリプトとその結果は、リポジトリの外の作業用ディレクトリに置く。
- 決めた結果をリポジトリに残すのは、次の手順で行う。
  同じ人が続けて行ってよい。
  - 規則の文書（`packages/eslint-plugin/docs/rules/`）は、
    eslint-plugin の SKILL の手順で書く。
    文書はそれぞれ、
    `packages/eslint-plugin/src/rules/` の規則のファイルに属する。
    規則は、eslint-plugin の SKILL のとおり、文書と一緒に足し、名前を変え、
    消す。
    落とした規則の文書が既にあれば、同じ手順で、規則のファイルと一緒に削除する。
  - 根拠の fixture が足りなければ、最小の入力と、
    その fixture が答える主張を添えて、tests パッケージに頼む。
    tests パッケージが足して mermaid.js
    の結果を記録し（`packages/tests/docs/maintaining-fixtures.md`）、
    届いた名前を規則の覚え書きに載せる。
- 主張ごとに、【実行】（動かして確かめた）、【読解】（読んで確かめた）、
  未確認を区別して示す。
  誤りと分かったら、その言葉で撤回する。
- 仕様は変わることがある。
  根拠にする前に、いまのファイルを読み直す。
- 作業ツリーをほかの作業と共有しているとき:
  - ほかの作業者が編集中のファイルに触らない。
    2 人が同じファイルを触ると、片方の変更が消える。
    編集が止まるのを待っても防げない。
  - 削除や置き換えの前に、対象の中身を読む。
  - git のステージを変えない。
    git mv、git rm も使わない。

## 2. 採否の基準と、その当て方

### 方針と基準

- 規則が報告するのは、書き手の誤りのうち、mermaid.js が黙って受理し、
  意図と違うものとして読むものである。
  打ち間違い、閉じ忘れ、壊れた JSON、id の使い回しなど。
  規則ごとに、普通の書き方の例を pin した mermaid.js で動かし、
  その例を整形して確かめる。
- 規則が報告する場合ごとに、mermaid.js の出力は、何かを失う、置き換える、
  効かなくする、書いていないものを加える、のどれかであり、その場合はそれを、
  どの値、どのテキストかまで言う。
  前の `accTitle` が置き換わる、方向の行のテキストが捨てられる、
  閉じが形に効かない、どの文も書かない状態ができる、がそうした事実である。
  score が 5 より大きい、`excludes` の知らない語のように、
  mermaid.js の文書が定める値域や語の外の値は効かず、その文書が根拠になる。
  mermaid.js が文法どおりに読み、何も失われない書き方は、
  書き手が別の構文のつもりだったと推定できても、規則にしない。
  ノードの行の `Write ::icon(fa fa-book)` は、
  ラベル `fa fa-book` を持つノード `Write ::icon` であり、
  `X(Foo)` が `X` でなく `Foo` を表示するのと同じである。
- 次の種類の規則は持たない。
  - 文体の規則。
    mermaid.js が書かれたとおりに読んでいて、
    後の編集で壊れることだけを防ぐもの。
  - 意図して分かりにくく書いたテキストのための規則。
  - mermaid.js の不具合のための規則。
    書き手が正しく意味の通る書き方をしているのに、
    mermaid.js が誤って読むもの（`subgraph Front end`、ラベルの中の CSS）。
    書き手に直すものはなく、規則が言えるのは不具合の避け方だけである。
    規則が頼るのは言語の定義でなく実装の欠陥なので、
    不具合が直った版の利用者には、正しい文を誤りと言う報告が出続ける。
    直す場所は mermaid.js への報告であり、lint の規則が吸収すると不具合が残る。
    これを mermaid.js に報告するかは別の問いで、ユーザーが決める。
    場合がそうした不具合であるのは、書き手に直すものがないときだけである。
    テキストが mermaid.js の文書の示すとおりに書かれ、ほかのどの書き方でも、
    失われるものを避けられないときである。
    その例は、`links` の中のフラグメントのある URL である。
    何も失わない形を文書が示しているときは、
    その場合は誤りのままである（`note left of A:hi`。文書は `:`
    の後に空白を置いて書く）。
    持つ規則の条件からは、木が誤りと見分けられるところでそうした不具合を除く。
    木が見分けられないところでは、7 節が言うとおり、
    誤りと一緒に報告する（ラベルの中の `direction LR` のテキスト）。
  - 条件が、書き手が意図した書き方にも当てはまる規則。
    `A[Issue #123; fixed]` は、エンティティ `#9829;` と同じ形をしている。
  - このプロジェクトのフォーマッターの出力で、
    mermaid.js の読み方が見える形になるもののための規則。
    `A---orders` は `A ---o rders` と印字される。
    規則にしても、保守するものが 2 つになるだけである。
  - 当面は、構文を知らないことから起きる誤りのための規則。
    その書き方が別の意味になることが、仕様の文法や本文に書いてあるもの。
    括弧のない `A"Start"`、スタイルの間の `;` など。
- 規則を共通の規則にするのは、
  木のうち全図種が共有する部分についての 1 つの定義で全図種を扱え、
  どの図種でも同じに振る舞うときだけである。
  そうでなければ図種の規則で、
  名前は `<図種>-` で始まる（文書は `docs/rules/<図種>-<名前>.md`）。

判断の前に毎回読む。
この節の残りでは、その当て方を例で示す。

### 判断の例（mermaid 12.0.0 で【実行】）

残したもの（書き手の側の誤りを、mermaid が黙って受け入れるもの）:

### 迷ったときの問い

1. その入力を書くのは、普通に図を書いている人か。
   仕様の珍しい例をなぞっていないか。
2. mermaid は、いま、書かれたものと違う結果を出すか。
   後の編集で壊れるだけなら文体の規則。
3. 規則の条件は、文書化された正しい書き方や、
   意図して書いた書き方にも当たらないか。
   当たるなら、誤検出なしに報告できないので持たない。
   報告しない例として、意図した書き方を必ず 1 つ mermaid で動かす。
4. その書き方が別の意味になると、仕様の文法や本文に書いてあるか。
   書いてあり、構文を知っていれば書かないなら、当面は持たない。
   書いてあっても、構文を知っている人がうっかり起こすものは残す。
   閉じ忘れ、打ち間違い、id の使い回しなど。
5. 報告する例をフォーマッターで整形すると、mermaid の読み方が見える形になるか。
   なるなら持たない（フォーマッターと二重に保守することになる）。
   フォーマッターは Db を変えないので誤りを直すわけではないが、
   整形すれば書き手が気づける。
   整形の手順は 4 節。
   字下げのずれや空白の付き方の違いのような弱い手がかりしか出ないものは、
   見える形とはしない。
6. 書き手は正しく意味の通る書き方をしているのに、
   mermaid がそれを誤って読んでいないか。
   ふつうに考えて不具合のような挙動なら、規則にしない。
   mermaid の保守者が不具合と認めたか、文書に書かれているか、
   直される見込みがあるかは、この判定を決めない。
   それらは、判定とともに事実として記録する。
   規則にするのは、書き手の側の誤りを mermaid が黙って受け入れるもの。
   mermaid に報告するかどうかは別の決定で、根拠を示せるものについて、
   ユーザーが決める。
   事実の記録のために、次の 3 つをする。
   (a) mermaid の文書の、その構文の節と、ページの冒頭の警告を読む。
   (b) issue と PR を、題（`in:title`）と本文の両方で、語を別々にして探し、
   探した語を記録する。
   (c) 誤った結果が、Db の値だけでなく、描かれた図で利用者に見えるかを言う。
   境界にあるもの（空の `%%` 行、行末の空白）は、
   両方の理由を付けて決定を求める。
7. 決めきれないときは、両方の理由を付けて決定を求める。

## 3. 材料の探し方

- 仕様: `packages/spec/docs/common.md` と
  `packages/spec/docs/diagrams/<図種>.md`。
  規則の「帰結」として書かれた、受理されるが意外な読み方の例を拾う。
- fixture: `packages/tests/fixtures/<図種>/` の `input.mmd`、`expected.json`、
  `ast.json`。
  名前が `lex-`、`gram-`、`db-` で始まるものに、意外な読み方の記録が多い。
- フォーマッターの制限: `packages/prettier-plugin-mmd/docs/<図種>.md` と
  `docs/compatibility.md`。
  空白 1 つや `;` 1 つで意味が変わる箇所が並んでいる。
- 既存の規則: `packages/eslint-plugin/docs/rules/`。
  同じものを出さない。
- 自分で探す: 書き手の側の誤りから始めて、mermaid を動かす。
  閉じ忘れ、打ち間違い、id の使い回し、壊れた設定の JSON、
  コメントアウトの残りなど。
  仕様の珍しい例から始めると、意図して分かりにくい入力ばかりになりやすい。
  普通の書き方を mermaid が誤って読む例が見つかったら、それは規則でなく、
  mermaid の不具合の候補として結果に示す。
  たとえば、subgraph の名前の普通の英単語 `end` が改行を取り込む例。

## 4. mermaid と parse() で確かめる手順

次のスクリプトを、リポジトリの外の作業用ディレクトリに `probe.mts` として置く。
`<repo>` は、リポジトリのルートの絶対パスに置き換える。
リポジトリの外のファイルからはパッケージ名が解決されないので、
ソースファイルを絶対パスで import する。
拡張子は `.mts` にする（top-level の `await` を使うため）。
Node は型の注記を取り除いて実行するので、
型だけの import は `import type` で書き、 `enum`、`namespace`、
引数のプロパティは使わない。

```ts
import { readFileSync } from "node:fs"
import { parse } from "<repo>/packages/parser/src/index.ts"
import type { Root } from "<repo>/packages/parser/src/index.ts"
import { runMermaid } from "<repo>/packages/tests/src/mermaid.ts"

const casesPath = process.argv[2]
if (casesPath === undefined) throw new Error("usage: probe.mts <cases.json>")
const inputs: string[] = JSON.parse(readFileSync(casesPath, "utf8"))

function withoutPositions(key: string, value: unknown): unknown {
  return key === "loc" || key === "range" ? undefined : value
}

for (const input of inputs) {
  console.log("INPUT", JSON.stringify(input))
  const outcome = await runMermaid(input)
  if (outcome.accepted) {
    console.log(
      "MERMAID accepted",
      outcome.diagramType,
      JSON.stringify(outcome.db),
    )
  } else {
    console.log("MERMAID rejected", outcome.error.message.split("\n")[0])
  }
  let root: Root
  try {
    root = parse(input)
  } catch (error) {
    console.log(
      "PARSER error",
      error instanceof Error ? error.message.split("\n")[0] : String(error),
    )
    continue
  }
  console.log(
    "TOKENS",
    root.tokens
      .map((token) => `${token.type}:${JSON.stringify(token.value)}`)
      .join(" "),
  )
  console.log(
    "COMMENTS",
    JSON.stringify(root.comments.map((comment) => comment.value)),
  )
  console.log(
    "DIRECTIVES",
    JSON.stringify(
      root.directives.map((directive) => ({
        name: directive.name,
        closed: directive.closed,
      })),
    ),
  )
  console.log("BODY", JSON.stringify(root.body, withoutPositions))
}
```

- 入力の一覧は JSON のファイルにする。
  シェルで直接書くと `\n` や引用符を誤るので、
  Python などで `json.dump` して作る。
  行末の空白が要る入力も、こうすれば正確に作れる。
- `node <作業用ディレクトリ>/probe.mts <cases.json>` で実行する。
  どのディレクトリから実行してもよい。
  結果はファイルに書き出してから読む。
  マシンが混んでいると、起動に数分かかることがある。
- 1 つの候補につき、次の 3 つを同時に流す。
  - 報告する例（普通の書き方）
  - 報告しない例（直した書き方）
  - 意図した書き方（2 節の問い 3。例: `#9829;`、`R&D`）
- 条件や提案の各主張は、その主張が分ける場合ごとの入力で確かめる。
  その場所で出会うほかの決まり（ディレクティブ、無視される `;`、コメント行、
  空行、行区切り、空の説明ブロック）ごとの入力でも確かめる。
  conventions の SKILL の「テストの実行」のとおりで、
  入力はこれらの場合から選び、生成しない。
- 規則の場合の表を示す前に、下の場合の種類に、その表を当てる。
  文書の文が触れる種類ごとに行を加え、文に書く前に mermaid.js で走らせる。
  - 後の行から値を取る文で、間に空行、コメント行、
    ディレクティブがある形（`%% c` の後や `%%{init: {}}%%` の後の行を取る、
    2 つ目の `accTitle:`）
  - 大文字小文字を問わず読むと文が言う語を、
    ほかの大文字小文字で書いた形（`TITLE`、`Until`）と、
    後の空白なしで書いた形（`untilb1`）
  - 前の文と比べる規則では、mermaid.js が何を残し何を捨てるかから、
    比べる相手（最初のもの、同じ種類の最初のもの、直前のもの）を先に決め、
    規則が分ける種類と形を混ぜた 3 つを書いて、
    最初の文と 3 つ目の正しい相手が違うようにし（同じ名前の requirement、
    element、requirement で、3 つ目は 2 つ目と比べる。直前と比べる規則では、
    間に空のブロックのような数えない値を挟んだ 3 つ目）、
    メッセージがその相手を名指すかを確かめる。
    同じ形の 3 つ目は報告 2 である。
  - そうした規則で、置き換える値と同じ値を設定する文。
    mermaid.js が同じ値として持つ別の書き方（両端の空白、文字列と同じテキスト、
    ほかの大文字小文字）も含む。
    何も失わないので、報告しない。
  - 規則が数えない値の種類のそれぞれ（空のブロック、コメント行だけのブロック、
    ディレクティブだけのブロック）
  - 規則が隣の規則と出会う入力（ユーザージャーニーの `A: 5:: x`、
    空の人と捨てられるテキスト）
  - 空の項目の連なりと、区切りだけの一覧（`a,,b`、`,`）
  - それぞれの形の対になる形（`after` に対する `until`、開始に対する終わり）
  - mermaid.js が読む値を終える文字（`.`、タブ、ASCII でない文字）と、
    CRLF で書いた行末
  - mermaid.js がまったく読まず、
    どの規則も報告しないデータ（gantt の 4 つの項目のデータ）
- `runMermaid` は、mermaid.js が検出するすべての図種で Db の要約を返す。
  正規化関数は、
  図種ごとに `packages/tests/src/normalizers/index.ts` に登録してある。
  `parse()` も、すべての図種を読む。
  結果が変わるかは、受理と拒否に加えて、Db の要約を比べて判断する。
- 木での現れ方は、`parse()` の結果に条件を当てて確かめる。
  条件は、ノードの欄、トークンの種類と値、`Root.comments`、
  `Root.directives` で書く。
  テキストを字句解析し直す条件は書かない。
  葉のノードの値の中を探す必要があるときは、そう明記する。
  木とトークンから見つけられないなら、そう書く。

### 整形して確かめる（2 節の問い 5）

報告する例をフォーマッターに通し、mermaid の読み方が見える形になるかを見る。
次のスクリプトを作業用ディレクトリに `format.mts` として置き、
`<repo>` をリポジトリのルートの絶対パスに置き換えて、
probe と同じように実行する。
prettier は、プラグインのパッケージが依存として持つものを、
絶対パスで import する。
プラグインが import する `@mmd-toolkit/parser` は、ソースではなく、
ビルド済みの `packages/parser/lib` に解決される。
parser のソースが変わっていたら、スクリプトを動かす前に、
`pnpm --filter @mmd-toolkit/parser run build` で lib を作り直す。
作り直さないと、古い parser で整形される。
parser のソースを直接 import する probe は、この影響を受けない。

```ts
import { readFileSync } from "node:fs"
import { format } from "<repo>/packages/prettier-plugin-mmd/node_modules/prettier/index.mjs"
import plugin from "<repo>/packages/prettier-plugin-mmd/src/index.ts"

const casesPath = process.argv[2]
if (casesPath === undefined) throw new Error("usage: format.mts <cases.json>")
const inputs: string[] = JSON.parse(readFileSync(casesPath, "utf8"))

for (const input of inputs) {
  const formatted = await format(input, {
    parser: "mermaid",
    plugins: [plugin],
  })
  console.log("INPUT    ", JSON.stringify(input))
  console.log("FORMATTED", JSON.stringify(formatted))
}
```

例: `A---orders` は `A ---o rders` になる【実行】。

## 5. 共通の規則か、図種の規則か

条件は、2 節の「方針と基準」の最後の項目である。
共通の構文（`common.md` の規則）が原因でも、
図種の字句解析器が吸収したり拒否したりするなら、共通にしない。

1. 全図種の一覧を、仕様の `packages/spec/docs/detection.md` の表から取る。
   表には、検出の順の全エントリーと、各図種の先頭の語が並んでいる。
   手で書いた一覧は使わない。
2. 図種ごとに、その先頭の語で始まる最小の図を作り、
   mermaid が受理することを確かめる。

   括弧内は、mermaid が返した図種の id。
   表にない図種は、その都度作って確かめる。
   - `sequenceDiagram`、改行、`A->>B: hi`（sequence）

  共通か図種か。
- 何を報告するか（1 文）。
- 理由: mermaid がどう読むか、なぜ普通の書き方で起き、

- 報告する例、報告しない例、意図した書き方の例。
  それぞれ mermaid の結果を付ける【実行】。
  受理される入力であること。
  例は、普通の書き方にする。
  振る舞いを確かめるために足した前置き（前の説明など）は、例に入れず、
  理由の文と fixture で示す。
- 木での現れ方: どのノード、欄、トークンで見つけるか。
  `parse()` で確かめた結果【実行】。
- 根拠の fixture: 既にあれば名前。
  なければ、足すべき最小の入力と対照例。
- `recommended` の設定が有効にするかと、その理由。
  7 節で決める。
- 提案と、提案を付けないならその理由。
  8 節で決める。
- オプションと、後で足すことを考えるオプションとそれを足す条件。

## 7. `recommended` に入れるか

規則を持つと決めたら、`recommended` の設定がそれを有効にするかを決める。
`recommended` は、ESLint のプラグインの通例どおり、
ほとんどの利用者が有効にしたい規則、
つまり報告がほぼいつも直すべき誤りである規則の集まりにする。
このプラグインの規則は、どれも、
そうした誤り（2 節の「方針と基準」の最初の項目）を報告するので、
次の 4 つの基準のどれかを満たさない場合のほかは、入れる。

1. **報告がいつも事実である。**
   規則が報告するどの場所でも、mermaid.js は、
   テキストを書き手のつもりと違う読み方をする（捨てる、別のものに読む、
   拒否する、前の値を置き換える）。
   mermaid.js が書き手のつもりどおりに読む場所も報告する規則は、入れない。
2. **意図した書き方を報告しない。**
   書き手がわざとそう書く形が、条件に当たらない。
   これは規則を持つ基準でもあるので、持つ規則はふつう満たす。
   満たすかに疑いが残る規則は、入れない。
3. **報告が、変わる見込みのある mermaid.js の振る舞いに乗っていない。**
   規則が頼る振る舞いを直す PR が開いている規則と、
   mermaid.js の保守者が直すと言っている規則は、入れない。
   mermaid.js が変わると、新しい版の利用者に、
   事実でなくなった報告が出るからである。
4. **直し方がはっきりしている。**
   報告を受けた書き手が、何に書き換えればよいかが分かる。

同じノードにあるために誤りと一緒に報告される、
mermaid.js の不具合のような振る舞いは、
入れるのを妨げない（flowchart-no-ignored-text が、
方向の行の上のテキストと一緒に報告する、
ラベルの中の `direction LR` のテキストなど）。
mermaid.js はそのテキストも捨てるので、報告は事実であり（基準 1）、
書き手はテキストを書き換えて避けられる（基準 4）。
規則がそれのために持たれているのではない、というだけである。

規則は 1 件ずつ、その文書に照らして、場合ごとに判定する。

1. 基準 1 では、文書が分ける場合ごとに、
   mermaid.js が書き手のつもりどおりに読む場所を報告していないかを調べる。
   文書自身が、mermaid.js は書いたとおりに読むが報告する、と書く場合も調べる。
2. 基準 2 では、場合ごとに 2 節の問いで調べる。
   報告が、出力が何を失う、置き換える、効かなくする、加えるかを、
   書き手のつもりの推定なしに言い、
   mermaid.js の文書が示す書き方を報告しないか、である。
   後で埋めるために残した空のブロックのように、
   書き手がその形をわざと書きうるところでは、そこで報告が何を言うかを注に書く。
3. 基準 3 では、規則ごとに mermaid.js の issue と PR を検索し、
   検索語と見つかったものを記録する。
4. 基準 4 では、何に書き換えればよいかを文書が書いているかを調べる。

判定は下の表に記録し、入れない規則には理由を書く。
表の後の注に、基準ごとに調べたことを書く。
規則のファイルは、この表から `recommended` を設定する。
共通の規則は入れる。
どれも、すべての図種で 4 つの基準を満たし（注が言うとおり、
すべての図種で実行）、その文書はすべての図種を書いている。

判定（mermaid 12.0.0）:

| ------------------------------------------- | -------- | ------------------------------------------------------------------------ |
| flowchart-no-ignored-text                   | 入れる   |                                                                          |
| flowchart-no-unclosed-description-block     | 入れない | 基準 1: `{` の後に、自分の `}` で終わる説明                              |

  後の行にあっても前のものを置き換える（文法と `populate` を読んだ。実行）。
  (2) なし。
  3 つの種類は別であり、前の空の説明は何も失わない。
  アイコンは `getNodeIcon` が設定なしに解決するとおりに比べるので、

  規則は設定を読まず、
  `defaultIconPack` が解決する名前は文書が述べる限界である。
  (4) 注釈は種類ごとに 1 つにする。
  名前は、それを注釈と呼ぶ文書に従う。
- treeview-no-duplicate-title、treeview-no-duplicate-description、
  treeview-no-empty-description-block: ツリービューは、
  タイトルと説明を同じに読むので、上の pie の規則の注を持つ（実行）。
  `title` は描かれず、比べない。
  ブロックの行の先頭の罫線の文字と、それで始まる行のタブは、
  文書が述べる限界である。
- treeview-no-unclosed-description-block: (1) `}` のないブロックは、

  説明は空のままである（終端記号を読んだ。実行）。
  (2) なし。
  条件は、`accDescr`、省ける空白かタブ、`{` の順で始まる引用符のない名前であり、
  普通の名前はそうならないので、規則を有効にする。
  引用符の名前は報告しない。
  (4) ブロックを閉じる。

class-no-inline-comment: コメントの後に空白だけの行があり、
その行の後にコメント行がないとき、
mermaid.js は次の行を書き手のつもりどおりに別に読むが、

mermaid.js が変わるかは定まっていない。
[#1646](https://github.com/mermaid-js/mermaid/issues/1646)（closed）の返信は、
行末のコメントに対応すべきだとし、
[#6401](https://github.com/mermaid-js/mermaid/issues/6401) は、
その振る舞いを意図どおりとしている（基準 3）。

flowchart-no-unclosed-description-block は `recommended` に入れない。
mermaid.js が書いたとおりに読むのに報告すると文書が書く場所があるからである。

## 8. 提案

規則を持つと決めたら、提案か自動修正を付けるかと、その中身を決める。
提案は、エディタで利用者が選んだときだけ適用される書き換えである。
書き換えの候補は、次の 5 つの基準をすべて満たすときだけ提案にする。
満たす候補がない規則には、提案を付けない。

提案を付けないことは、守りを要する提案を付けるより良い。
候補は、それが正しい条件を仕様の文 1〜2 文で書けるときだけ出す。
結果の parse、既知の差異ごとの判定、
図種ごとの例外がないと成り立たない候補は出さず、候補を守るために条件を足さない。
提案のない規則はそれで足りる。
報告のメッセージが、何が起きるかを言っている。
1 つの規則の中の場合でも同じである。
規則は、報告するすべての場所で書き換えを出す必要はない。
書き換えが正しいと仕様の文が言える場合にだけ出し、
ほかの場合（書き換えが難しいか、条件を文で書けない場合）は出さず、
守る条件を足した書き換えを出さない。
行を独り占めする文だけを消すことと、コメントのない範囲だけを詰めることは、
その場合の例である。

1. **候補が、報告した書き方から決まる少数である（1〜3）。**
   書き換えが書くものは、木とそのトークンの位置と、ノードの値から決まる。
   新しい名前が要る書き換え（打ち間違えた id を別の id に、
   使い回した id を新しい id に変える）は候補にしない。
   どの名前のつもりかをテキストは示さないからである。
2. **どの候補も、書き手のつもりでありうる。**
   結果は、その誤りをした書き手が書こうとした形の 1 つである。
   書き手のつもりにかかわらず、規則を黙らせるだけの書き換えは候補にしない。
3. **条件を仕様の文から書き、規則がその場所をもう報告せず、
   書き換えが新しい誤りを書かない。**
   どの書き換えも、規則を走らせるときに結果を parse しない。
   parse は 1 行に約 0.04 ms かかる（1,600 行で約 70 ms）。
   そのため、提案ごとに結果を parse すると、報告の数と図の大きさの積だけかかる。
   報告が 100 ある 1,000 行の図では lint のたびに約 9 秒かかり、
   エディタでは使えない。
   ブロック、ディレクティブ、逆引用符、
   名前が取っていた行を文に戻す書き換え（ブロックを `{` の行の終わりで閉じる、
   treeview の名前を閉じる、ディレクティブを閉じる、逆引用符の名前を閉じる）と、
   `;` で行を分ける書き換えは出さない。
   それらの行が文に戻るか、mermaid.js がそれをどう読むかは、
   結果の全文を parse し、既知の差異について調べないと分からず、その差異は、
   仕様が述べない mermaid.js の字句解析の手順を写すことになるからである。
   空のまま閉じていないブロックを閉じる書き換えは候補にしない。
   空のブロックを書き、no-empty-description-block がそれを報告するからである。
   ほかの規則が結果を報告してよいのは、書き手のテキストがもう持っていた誤りを、
   書き換えが見えるようにするときだけである。
   前の説明の後の閉じていないブロックを閉じると、
   テキストが説明を 2 度設定していることが見え、
   no-duplicate-description がそれを報告する。
   規則のテストは、その提案がこのように見えるようにしうる規則を、
   それぞれが示す誤りとともに挙げ、結果にほかの規則の報告があれば失敗する。
   それはこの節の記録が言い、fixture が示す。
   規則の文書は言わない。
4. **結果を mermaid.js がどう読むかが分かっている。**
   この節の記録と fixture がその読み方を持ち、
   例を mermaid.js で走らせて確かめる（実行）。
   提案のメッセージは書き換えだけを言う。
   ``Remove this `accTitle` statement.``、
   ``Remove the earlier `accTitle` statement.``、`Remove the empty block.`、
   `Close the block at the end of the text.` がそうである。
   規則を使う人は書き換えで提案を選び、結果を見るからである。
   メッセージに読み方の節は付けない。
   結果がどのみち示すことを言うだけで、
   同じ値を設定する 3 つの文の 2 つ目では偽になる。
5. **結果が、見えない空白に頼らない。**
   行末の空白でだけ読み方が変わる書き換え（`%%`
   の後に空白を足す）は候補にしない。
   エディタが保存のときに行末の空白を消すと元に戻るからである。

書き換えを提案でなく自動修正（`meta.fixable`。`eslint --fix`
とエディタが保存のときに当てる）にするのは、
次の 2 つがともに成り立つときだけである。
1 つ目に、結果が書き手のつもりだと疑いなく言え、
mermaid.js がそれをつもりどおりに読む。
テキストが許す書き換えがこの 1 つで、
書き手が別のつもりで書いたかもしれないものを、消しも足しもしない。
2 つ目に、書き換えを決めるものが、書き換える範囲と自分の文の中にある。
`--fix` は、同じテキストで見つけたすべての規則の修正のうち、
範囲が重ならないものを 1 回の通しでまとめて当て、それから lint し直し、
それを 10 回まで繰り返す（ESLint の `lib/linter/source-code-fixer.js` と
`MAX_AUTOFIX_PASSES`）。
そのため、ほかの行を読む条件を持つ修正は、
同じ通しのほかの規則の修正で誤りになりうる。
修正を差し止めるだけの条件は、その条件が探す形をどの修正も作らないなら、
ほかの行を読んでよい。
修正は後の通しで当たる。
自動修正を出す報告は、同じ書き換えの提案を出さない。
自動修正の条件が成り立たない報告では、その書き換えを提案として出す。
どの書き換えを自動修正にするかは、この節の終わりに挙げる。

規則の文書の本文は、提案に触れない（SKILL `eslint-plugin` の 3 節）。
提案や自動修正があることは生成する告知が言い、
それぞれのメッセージはその書き換えを言う。
書き換えごとに何を変えるか、どんな条件で出すか、結果を mermaid.js がどう読むか、
何を見えるようにしうるか、規則が提案を付けない理由、
それを説明する mermaid.js のソースへのパーマリンクは、この節に記録する。
実装はこの記録に従い、規則のテストがそれを確かめる。
読み方は、mermaid 12.0.0 で、
各規則の invalid の fixture について確かめた（実行）。

### 書き換えの種類

どの書き換えも、ディレクティブを一緒に消さない。
消すか置き換える範囲の中にディレクティブがあるときは、書き換えを出さない。
ディレクティブの設定も一緒に消えるからである。
sankey の `a,b,1%%{init: {"theme":"dark"}}%%_000` を `a,b,1000` と書き換えると、
受理されるが（実行）、ディレクティブは消え、それとともにテーマも消える。
範囲の隣のディレクティブはそのまま残る（block-no-spaced-class-id が消す、
ディレクティブの後の空白）。
ディレクティブの中の書き換え（no-invalid-init-directive、
no-duplicate-init-key）は、その引数だけを変える。
fixture: 上の sankey の値（出さない）と、
ディレクティブのない同じ規則の値（出す）。

- 文を消す: 文を、その行と行終端と一緒に消す。
  文が行を独り占めするときに限る。
  最初の行で前に、最後の行で後に、空白のほかの文字もコメントもなく、ほかの文、
  `;`、コメントが行を分け合わないときである。
  flowchart の、
  テキストを次の行に書いた `accTitle:` のように複数の行にわたる文は、
  そのすべての行と一緒に消す。
  ほかの文、`;`、コメントと行を分け合う文は消さない。
  `A --> B; accTitle: x` と `accTitle: style:#b;` はその行を保つ。
  重複では、mermaid.js は残った最後の説明かタイトルを使う（実行）。
  subgraph の中の説明は、Db では subgraph のメンバーでもあるので、
  消すとメンバーも変わる（実行）。
  fixture: それだけの行の文（出す）。
  行で後にほかの文がある文、`;` の後の文、行で後にコメントがある文（出さない）。
  テキストが次の行にある `accTitle:`（出す。両方の行を消す）。
- 前の文を消す: その後規則がこの文を報告しないときだけ出す（`accTitle: A`、
  `accTitle: A`、`accTitle: B` で 2 つ目の `A` を消すと、
  `B` が最初のものを置き換えたままで、基準 3 に反する。実行）。
  部分では、前の部分について同じである。
- eventmodeling の行の文を消す: `accTitle:` や `accDescr:` の行の形は、
  ふつう行でほかの文の後に書く（`eventmodeling accTitle: First`、
  `tf 01 evt Bought accTitle: Second`）。
  そうした行の文は前の ASCII の空白かタブを取り、
  その文字は行末か最初の `%%`
  までなので（`packages/spec/docs/diagrams/eventmodeling.ja.md` の共通の形）、
  前の文はその空白の前で終わる。
  そこでは、行でその文の後に何もないとき、その文を、前の空白とタブと一緒に、
  行終端を除いて行末まで消す。
  後に `%%` があるときは出さない。
  2 つの規則の invalid の fixture にある、そうした文 51 個をそう消すと、
  どれもパーサーと mermaid.js が受理し、
  mermaid.js はタイトルと説明のほかを前と同じに読む（実行）。
  fixture: ヘッダーの後（出す）、frame の後（出す）、
  後にコメントがあるもの（出さない）。
- 文の一部を消す（gitgraph-no-duplicate-option、radar-no-duplicate-option、
  quadrant-no-duplicate-style、venn-no-duplicate-style、
  usecase-no-duplicate-metadata、treeview-no-duplicate-annotation、
  no-duplicate-init-key、journey-no-empty-person）: その部分を、
  隣の区切り 1 つと一緒に消す。
  区切りが単独で残らず、一覧がその形を保つようにするためである。
  部分を `,` で区切る一覧（radar のオプション、quadrant と venn のスタイル、
  usecase の metadata、JSON のオブジェクトのメンバー、journey の人）では、
  その部分の前の `,` を消し、最初の部分ではその後の `,` を消す。
  どちらも、部分の側の隣の空白と一緒に消す。
  部分を空白で区切る一覧（gitgraph のオプション、
  ノードの行の treeview の注釈）では、その部分の前の空白を消す。
  文のただ 1 つの部分は、部分としては消さない。
  代わりに、文の条件で文を消す（radar のオプション、venn のプロパティ、
  usecase の更新）。
  `systemBoundary` の usecase の見出しでは、代わりに metadata のブロックを消す。
  境界の metadata はなくてよいと `packages/spec/docs/ast/usecase.ja.md`
  が書くので、文法はそれを許す。
  それだけの行にある treeview の注釈は、文の条件で、行ごと消す。
  結果は、それぞれの一覧の文法が許す形なので、ほかの確かめは要らない。
  gitgraph には、下のその規則に書く条件がある。
  fixture: 一覧の最初、途中、最後の部分（どれも区切りと一緒に出す）。
  文のただ 1 つの部分（文を消すか、文が行を分け合うなら出さない）。
  ノードの行の treeview の注釈と、それだけの行の注釈。
- 行終端をまたいで消すか詰める: 行終端を持つ範囲を消すか 1
  行に詰める書き換え（区切りの前後や括弧の中の、行をまたぐ空白、
  行をまたぐ文の一部、つなぐ行の前の改行）は、範囲にコメントがなく、
  範囲の最初と最後の行のほかの行が空か空白だけのときだけ出す。
  そうでないと、端の行をつなげたとき、コメントが後の文字を取るか、
  間の行が値に入ることがある。
  fixture: block-no-invalid-direction の `A<["x"]>(right`、`%% c`、
  `down)`（出さない。パーサーも mermaid.js も受理する。実行）と、
  `A<["x"]>(right ,`、空の行、` down)`（出す）。
- 空のブロックを消す: 文の条件で消す。
  flowchart では、空のブロックを消しても Db は変わらない（実行）。
  ディレクティブを持つブロックは、
  上のディレクティブの規則により消さない（実行。消すと、
  subgraph が `inheritDir` で得た方向を失う）。
  ブロックが説明を空にする図種（architecture、cynefin、gitgraph、packet、pie、
  radar、railroad、treemap、treeview、usecase、wardley）と、
  自分の文字を説明にする図種（eventmodeling）では、
  mermaid.js はそれから最後に残った説明を使い（実行）、
  no-duplicate-description が後の文を報告することがある。
  eventmodeling では、行の文と同じく、ブロックは行でほかの文の後にあり、
  後にほかの文が続くこともある（`eventmodeling accDescr {} tf 01 evt Bought`）。
  行の始めのブロックは拒否される（実行）。
  ただし `---` のブロックの後では行を独り占めし、文の条件が当たる。
  そこでは、ブロックを行で前にある空白とタブと一緒に消し、後にあるものは残す。
  この規則の invalid の fixture、eventmodeling のコーパス、
  問いから書いた入力（ヘッダーの後、frame の後、後に frame、`accTitle:`、
  コメントがあるもの、テキストの終わり、行をまたぐブロック）にある、
  そうしたブロック 19 個をそう消すと、どれもパーサーと mermaid.js が受理し、
  mermaid.js は説明のほかを前と同じに読む（実行）。
  fixture: それだけの行の空のブロック（出す）と、eventmodeling のほかで、
  行で文の後にあるもの（出さない）。
- ブロックをテキストの終わりで閉じる: `}`
  のないブロックが受理される図種（agentflow、flowchart、sequence、state、
  xychart）で、最後の行の後に `}` の行を足す。
  ブロックが `{` の行より後の行にテキストを持つときに限る。
  この書き換えは行を戻さない。
  閉じていないディレクティブを持つブロックには出さない。
  そのディレクティブから後は、
  ディレクティブが mermaid.js の読み方を決めるからである（実行。`d`、
  `more %%{wrap`、`A --> B` を持つブロックをテキストの終わりで閉じると、
  説明 `d` と `more --> B` になる）。
  テキストの終わりで開いたままの、`Long` と `text` の行を持つブロックは、
  テキストの終わりで閉じると、その 2 行を説明に持つ（実行）。
  見えるようにしうるもの: ブロックの前で説明を設定したときの
  no-duplicate-description（`accDescr: d` の後の `accDescr { x` を閉じると `x`
  になる。実行）。
  後の `}` が閉じるブロックも報告し、提案は出さない。
  `accDescr { first` の後の `B --> C`、`A{y}`、`D` の行は、説明 `first`、
  `B --> C`、`A{y` と頂点 `D` だけになる。
  `A{y}` の `}` がブロックを閉じるからである（実行）。
  条件は、ブロックのテキストが、ブロックの `{` より後の行に `{` を持ち、
  閉じる `}` がその行に単独でないことで、ブロックを閉じる `}` は、
  その行の形かデータブロックのもの（行をまたぐものも含む。`B{` の後の
  `y}`。実行）である。
  `}` の前にその行で空白とディレクティブしかないとき、後に何があっても、
  `}` はその行に単独である（`};`、`} C`。実行）。
  `accDescr {`、`uses { here`、`}` は書き手の `}` で閉じる。
  `{` の行の `}`（`accDescr { a { b }` は `a { b` になる）と、
  行に単独の `}`（`accDescr { x {` の後の `}` は `x {` になる）は、
  書いたとおりにブロックを閉じ、報告しない（実行）。

### 規則

下の各規則は、そこに挙げる書き換えを、上のその種類の条件で出す。
提案を付けないとある規則は、何も出さない。

- agentflow、architecture、cynefin、er、eventmodeling、flowchart、gantt、
  gitgraph、journey、packet、pie、quadrant、radar、railroad、requirement、
  sequence、state、timeline、treemap、treeview、usecase、venn（タイトルだけ）、
  wardley の `<diagram>-no-duplicate-description` と
  `<diagram>-no-duplicate-title`: この文を消す。
  前の文を消す。
  見えるようにしうるもの: テキストのない文が隠していた、
  後の文での同じ規則（`title First`、`title`、`title Third`。実行）。
- agentflow、architecture、cynefin、er、eventmodeling、flowchart、gantt、
  gitgraph、journey、packet、pie、quadrant、radar、railroad、requirement、
  sequence、state、timeline、treemap、treeview、usecase、
  wardley の `<diagram>-no-empty-description-block`: 空のブロックを消す。
- agentflow、flowchart、sequence、state、
  xychart の `<diagram>-no-unclosed-description-block`:
  テキストの終わりで閉じる。
  er、eventmodeling、radar、requirement、treeview、
  usecase のものは提案を付けない（基準
  3。ありうる閉じ方は行を戻す。ブロックがノードになる treeview では、
  名前を閉じることも行を戻す）。

    この文だけを消せるときも、前の値を残すのは推測である。
  - 空のブロックを消す（`<diagram>-no-empty-description-block`）と、
    journey-no-empty-person: 空のブロックや空の人は、
    後で埋める場所であることがあり、
    書き手がそこに何も書かないつもりだったとはテキストは示さない。
  - ブロックをテキストの終わりで閉じる:
    ブロックがどこで終わるつもりだったかをテキストは示さず、
    ブロックのテキストとして残る後の行は、文のつもりだったかもしれない。
  - block-no-mismatched-shape、block-no-mismatched-edge、
    mindmap-no-mismatched-shape: 2
    つの括弧か矢印のどちらが誤りかをテキストは示さない。
  - block-no-useless-width: 幅を消すと書き手が書いたものを失い、
    どこへ移すかは選ぶことである。
  - wardley-no-ignored-link-label: 2
    つのラベルのどちらのつもりかをテキストは示さない。
  - block-no-edge-in-composite-head: 辺は、
    宣言するブロックを辺の位置に置くので、
    `end` の後へ移すとそれらも動くことがある。
  - architecture-no-reversed-marker: 描画を保ってテキストを変えるが、
    書き手はテキストの向きのつもりだったかもしれない。
  - architecture-no-ungrouped-modifier: `{group}` を消すと、
    書き手のつもりだったグループ分けを失う。
    それには group の名前が要る。
  - radar-no-reversed-range: 順でなく、2 つの数のどちらかが誤りかもしれない。
  - journey-no-ignored-text: 3
    つ目からのコロンは人の名前のものかもしれない（`Meet at 10:30`）。
  - journey-no-invalid-score: score
    の後の文字はタスクのものかもしれない（`Write: 2 drafts` は人 `drafts`
    を得てしまう）。
  - sankey-no-invalid-value と treemap-no-invalid-value の小数の `,`: `1,5` は
    1.5 か 15 かが分からない。
  - venn-no-invalid-style-key で、
    ほかのプロパティが同じ属性を設定するとき: mermaid.js が使う値が変わり、
    書き手がそのつもりだったとはテキストは示さない。
