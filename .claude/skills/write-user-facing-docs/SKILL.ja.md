# ユーザー向けドキュメントの執筆

文書の形式と検査には、
リポジトリの[conventions][conventions]を使う。
このスキルでは、説明の意味と構成を扱う。

## ページで伝える内容を定める

- 依頼、合意した計画、既存の文書から、
  読者が行いたいこととページの目的を把握する。
  書いた文章を正当化するために、別の目的を作らない。
- 編集前にページ全体を読む。
  説明をどのページが担当するかの確認や、重複を避けるために必要なら、
  関連ページも確認する。
- この製品の挙動と、利用する外部ツールの挙動を区別する。
  外部ツールのオプションを扱う場合は、
  どれがこの製品に反映され、何を変えるのかを説明する。
  標準の既定値や挙動を、この製品が定義しているように書かない。
  外部ツールの詳細は、読者の目的に必要な場合に含める。
  ページを埋めるためだけにリファレンスを再掲しない。
- 見出しと導入文で、一覧や例が何を説明するのかを明確にする。
  名前と定義を並べるだけでは、この製品に関係する理由は伝わらない。
- 読者の目的を達成するのに役立つ参照リンクを付ける。
  リンクの目的がすでに明確なら、参照を促す一文を重ねない。

## 必要な情報を失わずに指摘を反映する

- 指摘が何を問題にしているかを特定してから修正する。
  ある種類の詳細を削る指摘を、
  同じ話題に関する説明すべてが不要だと解釈しない。
- 例の書き方や設定方針を変更するときは、編集前に、
  依頼された範囲のガイド内から同じ用途の例をすべて検索する。
  英語版と日本語版の両方に反映し、修正後に再検索する。
  異なる形を残す場合は、その例の用途に必要な理由を確認する。
- それ自体で役立つ説明と例を保つ。
  外部ツールのオプションの既定値や併用仕様を省くことは、
  この製品にどう反映されるかの説明まで削る理由にはならない。
- 見出し、前後の段落、例、リンクを含め、
  修正に関係する説明をまとまりとして見直す。
  変更は依頼された範囲に収める。
  この見直しを、無関係なページを書き直す許可と解釈しない。
- 英語版と日本語版に、意味の上で同じ修正を反映する。
  変更した行だけを照合するのではなく、
  必要な説明が両方に残っていることを確認する。

## 完成した文書を読者の立場で読む

- 編集後に、変更した各ページを通して読む。
  会話の内容や書き手の意図を、文書に書かれた説明の一部とみなさない。
  本文だけで読者の目的に答え、
  誰の挙動を説明しているかが分かることを確認する。
- 削除によって、説明のない見出し、設定の分からない例、
  ページが扱うと示した話題の説明不足が残っていないか確認する。
  前後の説明に矛盾や重複がないかも確認する。
- 挙動の説明を、対象に応じた仕様、実装、
  フィクスチャー、公式文書で裏付ける。
  例が、本文で説明した挙動を示していることも確かめる。
- 説明の適切さは、lint・書式・テスト・ビルドの結果とは別に評価する。
  検査が成功しても、見出しが分かりやすいこと、内容が役立つこと、
  必要な情報が揃っていることの保証にはならない。
- 依頼された範囲内の問題は、完了を報告する前に直す。
  依頼と根拠から意図が分かる場合に、
  この読み直しを逐一の確認としてユーザーに負わせない。
